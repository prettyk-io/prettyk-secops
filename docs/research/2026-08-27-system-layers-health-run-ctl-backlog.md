# Эпик HEALTH — Контракт жизнеспособности

## HEALTH-1: Базовый health-контракт для всех управляемых сервисов

**Что сейчас:** Часть сервисов вообще не имеет проверки готовности. Нет разницы между «процесс жив» и «сервис готов отвечать».

**Что должно получиться:** Оператор (или оркестратор) может в любой момент спросить любой сервис PrettyK о его состоянии и получить стандартный ответ: жив, готов к трафику, завершает работу.

| | |
|---|---|
| **Given** | любой сервис PrettyK запущен (Live, Auth, Target, LLM, любой другой) |
| **When** | оператор (или оркестратор) запрашивает состояние сервиса |
| **Then** | сервис возвращает: жив ли процесс, готов ли принимать пользовательские запросы, находится ли в режиме draining |
| **Given** | сервис жив, но критическая зависимость недоступна |
| **Then** | сервис сообщает: жив, но не готов |
| **Given** | сервис получил команду на остановку |
| **Then** | перестаёт принимать новые запросы, завершает текущие, сообщает draining |

**DoD:**
- [ ] Все управляемые сервисы возвращают стандартный ответ о своём состоянии
- [ ] Состояние «готов» отличается от «жив» — без подключения к PostgreSQL сервис сообщает «не готов»
- [ ] При остановке сервис переходит в draining и не принимает новую работу
- [ ] Ответ не содержит внутренних деталей (стектрейсов, паролей, имён таблиц)

**Out of scope:**
- Не делать отдельный «health manager daemon»
- Не добавлять Kubernetes probes как единственный механизм — контракт работает и под Compose
- Не блокировать запуск всех сервисов если один не готов — зависимости описываются на уровне Compose

---

## HEALTH-2: Compose hardening — реальная проверка готовности

**Что сейчас:** Compose-зависимости используют `service_started` — то есть «контейнер начал запускаться», а не «сервис готов».

**Что должно получиться:** Compose не запускает зависимый сервис, пока его зависимость реально не готова отвечать.

| | |
|---|---|
| **Given** | есть Compose-стек с сервисами |
| **When** | оператор запускает стек |
| **Then** | сервисы стартуют в правильном порядке: сначала инфраструктура, потом бизнес-логика |
| **Given** | PostgreSQL ещё не принимает соединения |
| **Then** | Auth Server не запускается и не падает с ошибкой подключения |
| **Given** | любой сервис упал |
| **Then** | Compose перезапускает его по политике restart |

**DoD:**
- [ ] Критические Compose-зависимости используют `condition: service_healthy`
- [ ] Сервисы, у которых нет healthcheck, получают его
- [ ] Startup-order гарантирует: инфраструктура (PG, Valkey, OpenBao) → бизнес-сервисы (Auth, Live, Target)

**Out of scope:**
- Не писать свой supervisor поверх Compose
- Не добавлять сложную логику «перезапускать только если три раза подряд упал»
- Не трогать Pure Box — он не использует Compose

---

## HEALTH-3: Execution readiness — готовность принять новый run

**Что сейчас:** Нельзя спросить систему «есть ли свободная мощность для запуска?».

**Что должно получиться:** Оператор (и планировщик) может спросить worker pool: «есть ли свободная мощность?» — и получить честный ответ.

| | |
|---|---|
| **Given** | worker pool запущен, все worker'ы заняты |
| **When** | оператор или планировщик спрашивает «можно новый run?» |
| **Then** | ответ: «нет, все слоты заняты» |
| **Given** | worker pool запущен, есть свободный worker с нужными возможностями |
| **When** | запрашивается готовность к запуску |
| **Then** | ответ: «готов, доступно N слотов» |

**DoD:**
- [ ] Worker pool сообщает количество свободных слотов
- [ ] Worker учитывает свои capabilities при ответе (есть браузер / нет браузера)
- [ ] При переходе в draining новые слоты не отдаются

**Out of scope:**
- Не делать этот эндпоинт частью публичного API
- Не смешивать с бизнес-логикой запуска

# Эпик EDGE — Единая точка входа и сетевая граница

**Что сейчас:** Каждый сервис (Vite :5173, Live :8767, Auth :3001, Terminal :3002) имеет свой открытый порт. scanner :8080 и PostgreSQL :5432 потенциально доступны снаружи в lab-режиме.

**Что должно быть:** Внешний мир видит один порт. Внутренние сервисы не выставляются наружу напрямую. Стандартный reverse proxy управляет TLS, маршрутизацией, WebSocket/SSE и базовой защитой.

---

## EDGE-1: Edge Gateway для self-hosted профиля

**Что должно получиться:** В production/self-hosted режиме все внешние запросы проходят через стандартный reverse proxy. Прямые порты сервисов закрыты от внешней сети.

| | |
|---|---|
| **Given** | развёрнут self-hosted профиль |
| **When** | пользователь открывает приложение |
| **Then** | все запросы идут через один порт (443) |
| **Given** | запрос требует WebSocket или SSE |
| **Then** | gateway корректно проксирует постоянное соединение без обрыва по таймауту |
| **Given** | прямой запрос на порт PostgreSQL или scanner |
| **Then** | запрос не доходит из внешней сети |

**DoD:**
- [ ] Один внешний порт для всего приложения
- [ ] TLS работает
- [ ] WebSocket/SSE не обрываются
- [ ] Внутренние сервисы (PG, Valkey, scanner, OpenBao, Grid) не exposed наружу
- [ ] Используется стандартный reverse proxy, не самописный

**Out of scope:**
- Не добавлять Kubernetes Ingress/Gateway API на первом шаге
- Не менять локальную lab-конфигурацию (loopback, всё на localhost)
- Не трогать Pure Box — он не имеет внешних портов

---

## EDGE-2: CORS и rate-limiting на уровне gateway

**Что должно получиться:** Gateway применяет единую политику CORS и защиту от перебора — не каждый сервис сам решает, кому отвечать.

| | |
|---|---|
| **Given** | запрос с неразрешённого origin |
| **When** | gateway получает cross-origin запрос |
| **Then** | запрос отклонён на уровне gateway |
| **Given** | слишком много запросов от одного источника |
| **When** | превышен лимит |
| **Then** | gateway возвращает 429, не пропуская запрос к бэкенду |

**DoD:**
- [ ] CORS настраивается в одном месте, не в каждом сервисе отдельно
- [ ] Базовый rate-limiting включён
- [ ] Легитимные запросы не блокируются

**Out of scope:**
- Не убирать CORS из сервисов, которые сейчас его настраивают — gateway добавляется поверх
- Не делать сложную WAF-логику

# Эпик RUN-CTL — Run Control Plane и жизненный цикл запуска

**КРУПНЕЙШИЙ ЭПИК.** Ядро недостающего системного слоя.

**Что сейчас:** Запуск — синхронный CLI-процесс. Если процесс упал — run потерян. Нет очереди, нет гарантии «ровно один раз», нет восстановления после падения worker'а.

**Что должно быть:** Каждый запуск — управляемая сущность с полным жизненным циклом. Пользователь создаёт запуск, система ставит его в очередь, назначает подходящий worker, следит за выполнением, собирает evidence. При падении worker'а запуск не теряется.

---

## RUN-CTL-1: Модель жизненного цикла запуска

**Что должно получиться:** Каждый запуск проходит через фиксированные состояния. Пользователь видит, где сейчас его запуск, и может на него повлиять.

| | |
|---|---|
| **Given** | пользователь создал запуск |
| **When** | запуск только создан и ещё не назначен worker |
| **Then** | статус: в очереди |
| **Given** | worker забрал запуск и начал выполнение |
| **Then** | статус: выполняется |
| **Given** | запуск завершён успешно |
| **Then** | статус: завершён, evidence привязан |
| **Given** | запуск завершился с ошибкой |
| **Then** | статус: ошибка, с указанием причины |
| **Given** | пользователь отменил запуск |
| **When** | запуск ещё в очереди |
| **Then** | статус: отменён, worker не получает задачу |
| **When** | запуск уже выполняется |
| **Then** | worker получает сигнал остановки, статус: отменён |

**DoD:**
- [ ] Все состояния жизненного цикла определены и видны пользователю
- [ ] Переходы между состояниями атомарны (нельзя «застрять» между двумя)
- [ ] Один и тот же запуск нельзя создать дважды (защита от двойного клика)
- [ ] Отмена работает и в очереди, и во время выполнения
- [ ] История состояний сохраняется (когда и почему изменился статус)

**Out of scope:**
- Не реализовывать автоматический retry на этом этапе (отдельная карточка)
- Не добавлять сложный workflow-движок с ветвлением условий
- Не привязывать к конкретной очереди или библиотеке

---

## RUN-CTL-2: Защита от дублирования запусков

**Что должно получиться:** Один и тот же запрос на запуск (повторный клик, повторный вызов API) не создаёт второй run.

| | |
|---|---|
| **Given** | пользователь создал запуск с определёнными параметрами |
| **When** | приходит повторный идентичный запрос в течение короткого времени |
| **Then** | система возвращает существующий run, а не создаёт новый |
| **Given** | первая попытка запуска уже завершена |
| **When** | приходит запрос на повторный запуск |
| **Then** | создаётся новый run (это уже новый запуск, не дубль) |

**DoD:**
- [ ] Двойной клик «Запустить» не создаёт два запуска
- [ ] Повторный вызов API с теми же параметрами не дублирует run
- [ ] Пользователь видит понятное сообщение, если запуск уже существует

**Out of scope:**
- Не блокировать намеренный повторный запуск того же теста спустя время

---

## RUN-CTL-3: Ограничение одновременных запусков

**Что должно получиться:** Система не позволяет запустить больше тестов одновременно, чем доступно worker'ов. Пользователь видит, сколько запусков в очереди перед ним.

| | |
|---|---|
| **Given** | все worker'ы заняты |
| **When** | пользователь создаёт новый запуск |
| **Then** | запуск становится в очередь |
| **Given** | запуск в очереди |
| **Then** | пользователь видит свою позицию в очереди и примерное время ожидания |
| **Given** | один worker освободился |
| **Then** | первый запуск из очереди назначается на него |

**DoD:**
- [ ] Запуски не стартуют, если нет свободной мощности
- [ ] Очерёдность соблюдается (FIFO)
- [ ] Пользователь информирован о позиции в очереди
- [ ] Система не падает при глубокой очереди

**Out of scope:**
- Не делать приоритеты запусков на этом этапе
- Не ограничивать количество запусков на уровне пользователя/tenant — только глобальный лимит

---

## RUN-CTL-4: Назначение запуска подходящему worker'у

**Что должно получиться:** Запуск с требованиями (нужен Chrome, нужен scanner, нужен доступ к network zone) получает worker с соответствующими возможностями.

| | |
|---|---|
| **Given** | запуск требует браузер Chrome |
| **When** | свободен только worker без браузера |
| **Then** | запуск ждёт, пока не освободится браузерный worker |
| **Given** | есть подходящий свободный worker |
| **When** | запуск назначается |
| **Then** | worker получает задачу и начинает выполнение |

**DoD:**
- [ ] Worker сообщает свои возможности (браузер, scanner, сетевые зоны, connectors)
- [ ] Запуск назначается только на подходящий worker
- [ ] Если подходящего worker'а нет — запуск ждёт в очереди

**Out of scope:**
- Не делать сложную систему тегов/атрибутов — начать с фиксированного набора capabilities
- Не балансировать нагрузку между несколькими машинами на этом этапе

---

## RUN-CTL-5: Worker lease и обнаружение зависших запусков

**Что должно получиться:** Система знает, что worker жив и работает над запуском. Если worker перестал отвечать — запуск не теряется, а передаётся другому worker'у.

| | |
|---|---|
| **Given** | worker взял запуск и выполняет его |
| **When** | worker периодически подтверждает, что жив |
| **Then** | система считает запуск активным |
| **Given** | worker перестал отвечать дольше допустимого времени |
| **When** | таймаут истёк |
| **Then** | запуск помечается как «зависший» |
| **Given** | запуск признан зависшим |
| **Then** | система может передать его другому worker'у или пометить как упавший |

**DoD:**
- [ ] Worker подтверждает, что жив, с заданным интервалом
- [ ] Запуск, чей worker замолчал, обнаруживается в течение минуты
- [ ] Зависший запуск не остаётся в статусе «выполняется» навсегда
- [ ] Передача запуска новому worker'у не создаёт дублирующего выполнения

**Out of scope:**
- Не делать автоматический retry для всех типов зависаний на этом этапе
- Не пытаться восстановить ровно то же состояние браузера — новый worker начинает заново

---

## RUN-CTL-6: Автоматический retry с классификацией ошибок

**Что должно получиться:** Система автоматически повторяет запуск только при инфраструктурных сбоях. При ошибке валидации или недоступности цели — не повторяет.

| | |
|---|---|
| **Given** | запуск упал из-за потери соединения с worker'ом |
| **Then** | запуск автоматически повторяется (ограниченное число раз) |
| **Given** | запуск упал из-за ошибки валидации манифеста |
| **Then** | запуск НЕ повторяется, пользователь видит причину |
| **Given** | запуск упал из-за недоступности target |
| **Then** | запуск НЕ повторяется, пользователь видит: «цель недоступна» |
| **Given** | исчерпано максимальное число повторов |
| **Then** | запуск помечается как окончательно упавший |

**DoD:**
- [ ] Инфраструктурные ошибки → автоматический повтор (до N раз)
- [ ] Ошибки валидации и target → мгновенный fail, без повторов
- [ ] Пользователь видит причину fail и количество попыток
- [ ] Максимальное число попыток ограничено

**Out of scope:**
- Не делать экспоненциальную задержку на этом этапе — начать с фиксированной
- Не добавлять ручной retry как отдельную кнопку (пользователь может создать новый run)

# Эпик TELEMETRY — Сквозная корреляция и наблюдаемость

**Что сейчас:** Live показывает SSE, логи пишутся, Allure собирает отчёты. Но нет сквозной связи между запуском, его попытками, шагами, worker'ом и evidence.

**Что должно быть:** Каждый запуск, попытка, шаг, worker и артефакт связаны сквозными идентификаторами.

---

## TELEMETRY-1: Сквозная идентификация всех сущностей запуска

**Что должно получиться:** Каждый запуск и все его производные (попытки, шаги, worker'ы, артефакты) имеют уникальные идентификаторы, связанные в цепочку.

| | |
|---|---|
| **Given** | создан запуск |
| **Then** | запуск получает уникальный идентификатор |
| **Given** | запуск выполняется |
| **Then** | каждая попытка и каждый шаг имеют свои идентификаторы, ссылающиеся на родительский запуск |
| **Given** | worker выполняет шаг |
| **Then** | идентификатор worker'а зафиксирован в контексте шага |
| **Given** | создан артефакт (скриншот, лог, scanner-отчёт) |
| **Then** | артефакт связан с конкретным запуском, попыткой и шагом |

**DoD:**
- [ ] Каждый запуск имеет уникальный идентификатор
- [ ] Попытки и шаги связаны с родительским запуском
- [ ] Worker зафиксирован в контексте выполнения
- [ ] Артефакты не «висят в воздухе» — всегда известно, к какому запуску они относятся

**Out of scope:**
- Не внедрять полноценный OpenTelemetry SDK на этом этапе
- Не добавлять распределённую трассировку между сервисами
- Не менять формат существующих артефактов

---

## TELEMETRY-2: Структурированные логи с контекстом запуска

**Что должно получиться:** Логи содержат идентификаторы запуска, попытки и шага. Можно найти все логи конкретного запуска, а не грепать всё подряд.

| | |
|---|---|
| **Given** | выполняется запуск |
| **When** | любое событие пишется в лог |
| **Then** | лог-запись содержит идентификаторы: запуска, попытки, шага |
| **Given** | оператор ищет логи запуска |
| **Then** | может отфильтровать всё, что относится к конкретному запуску |

**DoD:**
- [ ] Логи содержат контекст запуска
- [ ] Можно отфильтровать логи по конкретному запуску
- [ ] Формат логов не ломает существующие инструменты

**Out of scope:**
- Не менять систему сбора логов (файлы, Docker logs, syslog)
- Не добавлять централизованный aggregator

---

## TELEMETRY-3: Базовые операционные метрики

**Что должно получиться:** Оператор видит ключевые показатели системы: сколько запусков активно, сколько в очереди, сколько worker'ов живо, сколько запусков упало за последний час.

| | |
|---|---|
| **Given** | система работает |
| **When** | оператор запрашивает метрики |
| **Then** | видит: активные запуски, очередь, живые worker'ы, ошибки за период |
| **Given** | очередь растёт |
| **Then** | метрика «глубина очереди» увеличивается |
| **Given** | worker упал |
| **Then** | метрика «живые worker'ы» уменьшается |

**DoD:**
- [ ] Ключевые метрики доступны в машиночитаемом формате

# Эпик PROFILES — Разделение профилей развёртывания

**Что сейчас:** Есть понятие Pure Box (single-process), но граница с Enterprise-режимом размыта.

**Что должно быть:** Pure Box всегда остаётся single-process без очереди и внешних зависимостей. Enterprise-профиль получает все системные слои.

---

## PROFILES-1: Честный контракт Pure Box как самодостаточного режима

**Что должно получиться:** Pure Box не требует PostgreSQL, Valkey, очереди и worker pool. Все системные улучшения Enterprise-профиля не ломают Pure Box.

| | |
|---|---|
| **Given** | пользователь запускает Pure Box |
| **When** | система стартует |
| **Then** | не пытается подключиться к PostgreSQL, Valkey или очереди |
| **Given** | добавлены Worker Pool и очередь в Enterprise-профиль |
| **Then** | Pure Box продолжает работать как раньше — синхронный запуск in-process |

**DoD:**
- [ ] Pure Box не требует внешних сервисов
- [ ] Код системных слоёв (очередь, worker pool) не загружается в Pure Box
- [ ] Существующие тесты Pure Box проходят

**Out of scope:**
- Не добавлять в Pure Box «облегчённую очередь»
- Не менять способ запуска тестов в Pure Box
