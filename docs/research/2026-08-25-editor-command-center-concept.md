Да, именно так и надо. И по новой схеме сейчас **не режем бэклог и не лезем в код**. Я держу первый слой: архитектурный концепт и направление. Потом Gemini насытит его визуальным языком и discovery, после чего DeepSeek проверит на прочность и нарежет исполнителям.

# Luna: Editor как Security Workbench

Тезис:

> **PrettyK Editor — не Monaco в красивой рамке. Это рабочее место для создания, проверки, запуска и расследования security-сценариев.**

Tailwind здесь — не цель и не «давайте накинем классов». Это инструмент, чтобы собрать цельную оболочку Web IDE:

- плотную;
- управляемую;
- расширяемую;
- эстетически отличимую;
- понятную оператору, который одновременно работает с DSL, браузером, сканером, findings и evidence.

Сейчас на скриншоте уже есть хороший фундамент: тёмный рабочий стол, дерево слева, вкладки, Monaco в центре, узнаваемый бренд, cyan/violet-направление. Но это пока скорее **редактор с навигацией**, чем полноценный Web IDE.

Главная проблема не в цветах. Главная проблема — экран почти не сообщает:

- какой сейчас проект;
- какой target выбран;
- что можно запустить;
- валиден ли текущий DSL;
- где находятся ошибки;
- что происходит с последним запуском;
- как быстро перейти от строки к evidence;
- какой контекст сейчас активен.

То есть пространства много, но рабочего контекста на нём мало.

---

# 1. Информационная архитектура

## Сейчас

На экране одновременно конкурируют:

- верхняя навигация продукта;
- переключатель Studio / Editor;
- иконки действий;
- вкладки документов;
- левое дерево;
- Monaco;
- отдельные маршруты «Студия / Мониторинг / Результаты».

Для обычного приложения это терпимо. Для Web IDE нужно сильнее разделить уровни.

## Предлагаемая модель

```text
PrettyK Workbench
├── Global product shell
│   ├── PrettyK / текущий workspace
│   ├── Studio / Editor / Monitor / Results
│   └── user, language, command palette
│
└── Editor workspace
    ├── Explorer
    ├── Document tabs
    ├── Monaco editor
    ├── Context / Inspector panel
    ├── Problems / Console / Run panel
    └── Status bar
```

То есть верхняя шапка отвечает за **продукт**, а рабочая область — за **конкретную проверку и документ**.

## Что это даст

- меньше конкуренции между навигацией и рабочими действиями;
- понятная иерархия;
- возможность добавлять Browser, QWEN, Evidence и Inspector, не превращая шапку в пульт самолёта;
- единая модель для Studio и Editor.

# 2. Панели и компоновка

Я бы закладывал классическую IDE-модель, но не копировал VS Code.

```text
┌─────────────────────────────────────────────────────────────┐
│ Product shell / workspace / run / user                       │
├───────────────┬──────────────────────────────┬──────────────┤
│ Explorer       │ Document tabs                │ Context      │
│                ├──────────────────────────────┤ Inspector    │
│ project tree   │                              │ Browser      │
│ pages          │ Monaco / DSL                 │ Variables    │
│ scenarios      │                              │ QWEN         │
│ fuzzers        │                              │ Evidence     │
│ modules        │                              │              │
├───────────────┴──────────────────────────────┴──────────────┤
│ Problems / Output / Run / Evidence / Terminal                │
├─────────────────────────────────────────────────────────────┤
│ Status bar: target · validation · sync · cursor · run state   │
└─────────────────────────────────────────────────────────────┘
```

Все три дополнительные зоны должны быть:

- сворачиваемыми;
- ресайзируемыми;
- запоминающими состояние;
- открываемыми горячими клавишами;
- независимыми от конкретного документа.

Ключевой принцип: **не показывать всё постоянно**. Web IDE должна быть плотной, но не душной.

---

# 3. Editor как IDE

Здесь есть два слоя.

## Базовые возможности Monaco

Нужно охватить весь нормальный IDE-набор:

- quick open;
- command palette;
- поиск по workspace;
- поиск и замена;
- multi-cursor;
- folding;
- sticky scroll;
- breadcrumbs;
- minimap — опционально, если не создаёт шум;
- go to definition;
- go to line;
- peek definition;
- rename;
- форматирование;
- snippets;
- code actions;
- diff между версиями;
- dirty-state вкладок;
- восстановление последнего положения курсора;
- понятные маркеры диагностики.

Сейчас редактор выглядит красиво, но довольно статично. Пользователь должен чувствовать, что это настоящий рабочий инструмент, а не просто большой текстовый блок.

## DSL-aware возможности

Вот здесь появляется наше отличие от обычного Web IDE:

- подсветка не только синтаксиса, но и смысла шагов;
- дерево шагов документа;
- быстрый переход к `Пусть`, `Секрет`, `Открыть`, `Нажать`, `Проверить`;
- список переменных и их использования;
- переход из шага к странице, модулю, профилю авторизации;
- inline-диагностика с объяснением;
- «запустить этот шаг»;
- «проверить этот конструктор»;
- визуальный preview wire-формата;
- связь строки DSL с реальным execution step;
- переход из ошибки в нужный участок;
- переход из finding обратно в строку, которая его породила.

Последний пункт очень важен. Мы строим не просто авторинг, а **traceability**:

```text
DSL line
  → execution step
  → request / browser action
  → finding
  → evidence
  → remediation
```

Это и есть enterprise-ценность Editor.

# 4. Security-контекст должен быть всегда виден

Обычный редактор может позволить себе скрывать контекст. Security IDE — нет.

В рабочей области постоянно, но ненавязчиво должны быть видны:

- текущий target;
- environment;
- выбранный browser/runtime;
- активный auth profile;
- scope;
- последний validation status;
- состояние сохранения;
- текущий run;
- режим: Draft / Validated / Running / Failed / Completed.

Особенно важен target. Оператор не должен нажимать «Запустить» и только потом вспоминать, по какому URL работает сценарий.

Пример:

```text
TARGET  juice-shop.local
SCOPE   included · 12 domains
AUTH    juice-shop-user
BROWSER chrome-headless
STATUS  validated
```

Эта информация может жить в правой панели и статус-баре, но не должна исчезать полностью.

## Безопасность интерфейса

Нужно сразу закладывать:

- секреты никогда не показываются plaintext;
- clipboard-копирование секретов требует явного действия;
- логи и terminal автоматически redacted;
- опасные действия имеют понятное предупреждение;
- запуск против target вне scope блокируется;
- preflight failure виден до запуска;
- результат gate не маскируется красивой зелёной анимацией.

---

# 5. Run и Debug прямо из Editor

Кнопка «Запустить» в шапке — слишком грубая модель. Нужна градация:

- Validate document;
- Validate current step;
- Run current step;
- Run from current step;
- Run scenario;
- Run full check;
- Open War Room;
- Open latest results.

Для каждой команды должен быть понятный feedback:

```text
Validate → diagnostics
Run step → локальный результат
Run scenario → progress + console
Run full check → War Room / Live
Results → findings + evidence
```

Editor не должен конкурировать с War Room. Он должен быть точкой входа:

- автор написал;
- проверил;
- запустил;
- при необходимости перешёл в War Room;
- после завершения вернулся к конкретной строке или finding.

---

# 6. Нижняя панель

Нижняя панель — один из самых полезных элементов Web IDE.

Там могут жить вкладки:

- **Problems** — ошибки DSL, предупреждения, preflight;
- **Output** — технический лог;
- **Run** — текущая последовательность шагов;
- **Evidence** — собранные артефакты;
- **Terminal** — команды и gateway;
- **Findings** — краткий список результатов.

Важно: это не шесть панелей одновременно. Это один управляемый drawer с вкладками.

Полезная деталь — панель должна уметь открываться автоматически только при событии:

- появилась ошибка;
- стартовал запуск;
- обнаружен finding;
- пришёл terminal output.

---

# 7. Context Panel

Правую панель я бы сделал главным местом роста Editor.

В ней могут быть режимы:

## Inspector

- текущий шаг;
- action;
- strategy;
- значение;
- связанные переменные;
- linked page/module;
- execution status.

## Browser

- живая браузерная сессия;
- элемент, выбранный через discovery;
- клик по браузеру → связь со строкой;
- текущий URL;
- network/console hints.

## Variables

- все переменные сценария;
- тип;
- источник;
- secret/non-secret;
- usage count;
- переход к месту использования.

## QWEN

Не «чат сбоку ради AI», а контекстный аналитик:

- объясни эту ошибку;
- почему шаг не прошёл;
- покажи связанные findings;
- предложи исправление;
- объясни policy gate;
- свяжи evidence с текущей строкой.

## Evidence

- screenshots;
- request/response;
- console;
- trace;
- finding;
- reproduction command.

# 8. Эстетика и Tailwind

Tailwind нужен, но применять его надо дисциплинированно.

## Канон

- CSS variables — источник токенов;
- Tailwind — способ композиции;
- Monaco theme — отдельный адаптер к тем же токенам;
- два режима: Meta Dark и Meta Light;
- cyan/violet — брендовая база;
- semantic colors — только для реальных состояний: ошибка, warning, success;
- никаких случайных оранжевых, кислотных и ретро-панелей ради «живости»;
- плотность: Compact / Comfortable;
- focus state и keyboard navigation — часть дизайна, а не последующая полировка.

## Визуально я бы улучшал не количеством свечения

На текущем экране уже достаточно атмосферы. Следующий уровень — это:

- лучшее разделение поверхностей;
- ясная активная вкладка;
- более сильная типографическая иерархия;
- аккуратные borders;
- понятные hover/focus states;
- хороший spacing;
- компактные статусные чипы;
- спокойная анимация переходов;
- отсутствие визуального шума.

PrettyK должен выглядеть как **инструмент серьёзной AppSec-команды**, а не как cyberpunk-dashboard из Dribbble.

---

# 9. Сохранность и серверная модель

Это обязательно нужно заложить архитектурно, учитывая наш вчерашний косяк с `localStorage`.

Editor должен работать с понятной моделью:

```text
Server source of truth
        ↓
Workspace snapshot
        ↓
Local UI state / cache
```

В localStorage можно хранить:

- ширину панелей;
- активную вкладку;
- положение курсора;
- пользовательскую плотность;
- последний layout.

Нельзя считать localStorage источником истины для:

- checks;
- Wired;
- runs;
- findings;
- auth;
- evidence.

Нужны:

- draft state;
- dirty indicator;
- autosave status;
- conflict detection;
- restore after restart;
- version/history;
- честное состояние «не синхронизировано».

---

# 10. Доступность и скорость

Это не второстепенно. Web IDE будут использовать долго.

Нужно предусмотреть:

- полную клавиатурную навигацию;
- видимый focus;
- shortcut reference;
- `⌘K` / `Ctrl+K`;
- reduced motion;
- контраст;
- масштабирование текста;
- быстрый старт без загрузки всех панелей;
- lazy load Browser, QWEN и тяжёлых визуализаций;
- не пересоздавать Monaco при смене layout;
- не рендерить весь проектный граф при каждом вводе символа.

---

# Что не надо делать

Я бы сразу поставил ограничения:

1. Не превращать Editor в копию VS Code.
2. Не добавлять AI-чат без связи с DSL, run и evidence.
3. Не показывать все возможные панели одновременно.
4. Не прятать DSL за визуальным конструктором.
5. Не делать отдельные независимые state-машины для Editor, Studio и War Room.
6. Не хранить рабочие данные только в браузере.
7. Не использовать Tailwind как повод переписать весь фронтенд.
8. Не превращать каждый статус в цветную анимацию.
9. Не начинать с красивых микродеталей до утверждения layout и information architecture.

# Мой предлагаемый первый PoC

## Editor Command Center

Не полноценный Editor 2.0, а проверка новой оболочки:

```text
Tailwind shell
+ left Explorer
+ center Monaco
+ right Context panel
+ bottom Problems/Output drawer
+ status bar
+ command palette
+ target/run context
```

В PoC не надо сразу полноценно реализовывать:

- Browser;
- QWEN;
- Evidence;
- сложный collaboration;
- весь execution runtime.

Но оболочка должна иметь для них настоящие extension points, а не захардкоженные заглушки.

### Цель PoC

Проверить, что:

1. Editor ощущается как Web IDE, а не как текстовое поле.
2. Рабочий контекст виден без перегруза.
3. Панели складываются и раскрываются предсказуемо.
4. Monaco остаётся стабильным и не теряет состояние.
5. Run/Validate/Problems естественно живут рядом с кодом.
6. Tailwind позволяет держать единый visual system.
7. Архитектура готова к Browser, QWEN, Evidence и War Room.

Мой вердикт: **да, этим надо заморочиться всерьёз**. Editor вполне может стать главным лицом PrettyK. Не потому что там будет больше кнопок, а потому что он станет местом, где security intent, выполнение и доказательства соединяются в одну понятную рабочую среду.

Следующий ход по новой традиции:

1. **Gemini** — превратить эту архитектуру в конкретный visual/discovery-концепт: layout, панели, states, density, tokens, reference screens.
2. **DeepSeek** — проверить контракт, убрать лишнее, найти технические риски и нарезать PoC на Boss/Flash.
3. **Boss/Flash** — исполнение.

Сейчас я бы не добавлял ничего в код. Концептуальное направление уже достаточно ясное для передачи Gemini.
