## Раунд 1: Как конкуренты менеджат сущности проверки

**Ключевой вывод: НИКТО не нарезает болванки с assign'ом.** Это наша уникальная фишка для SecOps.

### aqua cloud (ALM)

```
Organization
  └── Project
       ├── Requirements (требования)
       ├── Test Cases (ручные тест-кейсы, пишут QA сами)
       ├── Test Runs (прогон набора кейсов)
       └── Defects (баги)
```

- **Болванок НЕТ.** Тест-кейсы создают инженеры с нуля. AI может генерировать из требований (NLP), но это те же тест-кейсы, просто автогенерённые. Никакого централизованного provisioning.
- **Иерархия ролей:** Organisation Admin → Project Manager → Tester → Read-only.
- **Видимость:** Project-based. Кто в проекте — тот видит его кейсы и прогоны.
- **Admin-панель одна:** Organisation-level settings (пользователи, лицензии, интеграции Jira/Jenkins).

### Testim (Tricentis)

```
Workspace
  └── Project
       └── Test → Test Suite → Plan → Run
```

- Тоже **нет assign'а болванок.** Инженер заходит в проект, пишет тест сам или записывает через recorder.
- **Админка:** Workspace-level. Управление пользователями, окружениями, CI-хуками.

### ACCELQ

```
Project
  └── Application (тестируемое приложение)
       └── Module → Scenario → Test Case → Run
```

- Полностью user-driven. Никаких шаблонов «сверху».
- Ролевая модель: Admin → Project Lead → Engineer → Viewer.

### Общий паттерн конкурентов

| Аспект | Все конкуренты (aqua, Testim, ACCELQ) |
|---|---|
| **Создание тестовых сущностей** | User-driven. Инженер сам создаёт сценарии с нуля или через recorder |
| **Admin provisioning** | Управление пользователями, доступами, окружениями, лицензиями. Не тестовыми сущностями |
| **Болванки / assign** | ❌ Отсутствуют |
| **Иерархия** | Плоская: Org/Workspace → Project → Test → Run |
| **Multi-tenancy внутри** | SaaS-разделение аккаунтами. Нет логических доменов внутри одного экземпляра |

### Почему у нас есть смысл в болванках (для SecOps)

В ИБ-контексте разделение труда реально существует:
- **Админ ИБ** знает **ЧТО** проверять: реестр приложений компании, compliance-объём, план проверок на квартал.
- **Сек-эксперт** знает **КАК**: наполняет сценариями, настраивает векторы атак, анализирует находки.

Болванка — это контракт между ними: админ ИБ создаёт Blank (имя, scope, дедлайн, политики гейтов), назначает на эксперта. Эксперт получает готовый каркас и наполняет его.

**В Automation Lab этой потребности нет.** QA-инженер сам знает и что тестировать, и как. Поэтому Automation Lab — чисто user-driven, без assign'а.

## Раунд 2: Проектируем иерархию PrettyK

Два продукта — две немного разные модели, но общий скелет.

### Общая иерархия сущностей (единая для обоих продуктов)

```text
ORGANIZATION (компания-покупатель: «Сбербанк», «ВТБ», etc.)
│   Одна Org = один экземпляр коробки. Создаётся при установке.
│
├── DOMAIN / SPACE (логическое подразделение: «Департамент ИБ», «QA Отдел Розницы»)
│   │   Создаётся админом уровня Org или домена.
│   │   Это НЕ URL, а логическая группировка проектов, пользователей и доступов.
│   │
│   ├── PROJECT (тип: Automation или Security — фиксируется при создании)
│   │   │
│   │   ├── CHECK / SCAN (один экземпляр проверки)
│   │   │   │
│   │   │   ├── SCENARIO (DSL-сценарий: Open → Type → Click → Assert)
│   │   │   ├── RUN #1 (прогон — success/failure + screenshots + logs)
│   │   │   ├── RUN #2
│   │   │   └── ...
│   │   │
│   │   └── [только в SecOps] BLANK TEMPLATE (болванка, созданная admin_sec)
│   │        │   admin_sec создаёт Blank из реестра приложений
│   │        │   Assign'ит на sec_expert
│   │        │   sec_expert наполняет DSL-сценариями
│   │
│   └── USERS (с ролями в рамках домена)
│
└── [только в SecOps] POLICIES (политики гейтов: уровня Org или Domain)
```

### Ключевое различие Automation vs SecOps

| Аспект | Automation Lab | SecOps Lab |
|---|---|---|
| **Кто создаёт проект** | QA-инженер сам | admin_sec или эксперт |
| **Болванки (Blank Templates)** | ❌ Нет | ✅ admin_sec нарезает из реестра, назначает эксперту |
| **Сценарии** | Инженер пишет с нуля или Discovery Engine | Эксперт наполняет болванку DSL-сценариями |
| **Consumer при запуске** | Actions/Probes (чистая автоматизация) | Actions + ZAP/Fuzzer/Dojo consumer |
| **Dashboard** | Скриншоты, логи, пошаговый разбор | Severity breakdown, Dojo links, gate status |
| **Политики гейтов** | ❌ Нет | ✅ На уровне Org или Domain |

### Где и как держим

| Сущность | Хранение | Примечание |
|---|---|---|
| **Organization** | Конфигурация коробки | Одна Org = один docker-compose экземпляр |
| **Domain / Space** | Коллекция в БД, FK → Org | Логическая группировка. Не URL, не vhost |
| **Project** | Коллекция в БД, FK → Domain | Тип (automation \| security) фиксирован при создании |
| **Check / Blank** | Коллекция в БД, FK → Project | Blank — специальный тип Check с `created_by: admin_sec`, `assigned_to: sec_expert` |
| **Run** | Документ в БД, FK → Check | Каждый запуск — отдельная запись: статус, артефакты, метаданные |
| **User** | Коллекция, FK → Org + [Domain roles] | Ролевая модель на уровне Org и Domain |

```text
┌─────────────────────────────────────────────────────────┐
│  CONTROL PANEL — PRETTYK BOX                            │
│  Organization: «Сбербанк»                                │
│                                                         │
│  [ Демоны ]  [ Retention ]  [ Vault ]  [ Logs ]        │
│                                                         │
│  DOMAINS:                                               │
│  ┌─────────────────────────────────────────────────┐    │
│  │ 🏢 Департамент ИБ          │ 12 users · 5 proj  │    │
```

| Фича | aqua / Testim / ACCELQ | PrettyK |

| **Один DSL на два продукта** | ❌ (разные продукты = разные форматы) | ✅ Общий Wired/DSL для Automation и Security |

## Открытые вопросы для следующего раунда (Luna + Gemini)

1. **Domain как коллекция в БД или как физически изолированный tenant?** Для airgap-коробки логического разделения достаточно. Но нужно проверить: не просядет ли производительность при 50+ доменах и 1000+ проектов в одном инстансе.
2. **Нужна ли иерархия доменов (parent → child)?** Например: «Департамент ИБ» → «Отдел AppSec» → «Группа внешнего тестирования». Или плоская структура достаточно.
3. **Как технически реализовать assign болванки?** Blank — это специальный тип Check с полями `created_by`, `assigned_to`, `status: draft | assigned | in_progress | completed`. Или отдельная коллекция?
4. **Нужен ли audit log на уровне домена?** Кто создал, кто назначил, кто запустил, кто менял политики.
5. **Dashboard видимость:** фильтровать на API-уровне (по ролям) или на UI-уровне (все данные приходят, фронт скрывает)?

## Раунд Luna: инженерная ревизия модели

> **Голова:** Luna / engineering evaluation · Mountain View · 23 августа 2026.
> Цель раунда — проверить, что продуктовая идея не заставляет нас преждевременно размножать runtime, сущности и права.

## Вердикт

Направление правильное: **Automation Lab и SecOps Lab — разные коммерческие продукты, но единая модель сущностей и единый runtime.**

В исходном черновике есть три опасных смешения:

1. `Organization = docker-compose instance` — это упаковка, а не сущность доменной модели.
2. `Domain / Space` — пока два названия одного уровня. Нужно выбрать одно каноническое слово.
3. `Blank` не должен быть особым видом `Check`. Болванка — это шаблон или work item, а assign — отдельная связь/задача.

## Раунд 1 Luna: что реально можно говорить о конкурентах

По публичным сайтам мы видим UX и продуктовую терминологию, но не внутреннюю БД aqua, Testim или ACCELQ. Поэтому тезис «у них нет болванок» следует считать **неподтверждённой гипотезой**, а не фактом.

Типовой публичный паттерн таких систем:

```text
Account / Organization
  └── Workspace / Project
       ├── Test case / Scenario
       ├── Suite / Plan
       ├── Schedule / Trigger
       └── Run / Result
```

В enterprise-режиме у них могут существовать шаблоны, workflow approval, назначение тестов, обязательные test plans, ownership и SLA. При этом они могут называться `Template`, `Test Plan`, `Work Item`, `Assignment` или `Campaign`, а не `Blank`.

### Для чего нужны болванки

Не для того, чтобы админ писал тест за инженера. Они нужны для:

- стандартизации обязательного объёма проверки;
- разделения ответственности: админ определяет **что проверить**, эксперт — **как проверить**;
- compliance и аудита;
- назначения владельца и дедлайна;
- повторяемых квартальных/регламентных проверок;
- контроля покрытия приложений;
- запрета самовольного изменения scope.

Для Automation Lab нормальный путь — user-driven:

```text
QA создаёт проект → сам пишет сценарий → сам запускает
```

Для SecOps разумен enterprise-workflow:

```text
Admin ИБ создаёт work item → назначает эксперту →
эксперт наполняет/исполняет → результат проходит policy gate
```

## Раунд 2 Luna: рекомендуемая иерархия PrettyK

### Канонический термин — Space

Я рекомендую выбрать **Space**, а не одновременно `Domain / Space`:

- `domain` легко перепутать с web-доменом цели;
- `space` соответствует команде или подразделению;
- в UI понятнее: `Organization → Spaces`;
- Space может быть «Департамент ИБ», «QA Розницы» или «Команда Mobile».

### Общая модель

```text
INSTALLATION / BOX
└── ORGANIZATION
    ├── SPACES
    │   ├── Members + roles
    │   ├── Projects
    │   │   ├── Scenarios / Checks
    │   │   ├── Suites / Plans
    │   │   └── Schedules / Triggers
    │   ├── Assignments
    │   └── Runs
    │       └── Artifacts
    │
    ├── Application / Target Registry
    ├── Policies
    └── Audit Log
```

### Сущности

| Сущность | Смысл |
|---|---|
| **Installation / Box** | Физическая поставка PrettyK; не смешивать с бизнес-организацией |
| **Organization** | Покупатель, например Сбербанк |
| **Space** | Логическая команда/подразделение внутри Organization |
| **Project** | Контейнер работы: Automation или Security |
| **Scenario / Check** | Исполняемое описание проверки |
| **Suite / Plan** | Набор сценариев для совместного запуска |
| **Assignment** | Административная задача: кому, что и до какого срока выполнить |
| **Run** | Неизменяемый факт конкретного исполнения |
| **Artifact** | Screenshot, logs, traces, reports |
| **Schedule / Trigger** | Причина автоматического запуска |
| **Policy** | Правило допуска, gate или compliance |
| **Audit Log** | Кто и что менял |

### Главная правка модели Blank

Не делать так:

```text
Blank = особый Check
assigned_to = поле внутри Check
```

Делать так:

```text
Check / Scenario
Assignment
  ├── assignee
  ├── due date
  ├── scope
  ├── policy snapshot
  └── status
```

Это позволяет один шаблон назначить нескольким экспертам, переназначать работу, сохранять историю и полностью не включать Assignment в Automation Lab.

Для SecOps поток выглядит так:

```text
Security Template
   ↓ instantiate
Security Check
   ↓ assign
Assignment
   ↓ execute
Run
```

### Хранение и границы

- `Box` и `Organization` разводим концептуально, даже если сегодня один Box содержит одну Organization.
- Все бизнес-сущности принадлежат Organization.
- Проекты и содержимое принадлежат Space.
- Run хранится как исторический snapshot, чтобы переименование проекта не ломало историю.
- Большие артефакты не смешиваются с основной записью Run.
- Секреты не попадают в Project/Run, только ссылки на Vault.
- Audit Log — append-only.
- Доступ вычисляется сервером; фронтенд не получает чужие данные с последующим скрытием.

## Раунд 3 Luna: продукты и роли

### Automation Lab

```text
Organization
  └── Space
       ├── Space Admin
       ├── QA Users
       └── Automation Projects
            ├── Scenarios
            ├── Suites
            ├── Schedules
            └── Runs
```

- пользователь сам создаёт проект;
- сам создаёт сценарии;
- сам запускает и смотрит результаты;
- обязательных болванок нет;
- ZAP, Dojo и security gate не входят в профиль;
- есть screenshot, logs, status и history.

### SecOps Lab

```text
Organization
  └── Space: «Департамент ИБ»
       ├── admin_sec
       ├── sec_expert
       ├── Security Registry
       ├── Security Templates
       ├── Assignments
       ├── Policies
       └── Security Projects / Checks / Runs
```

- `admin_sec` управляет приложениями, scope, шаблонами, policies и назначениями;
- `sec_expert` выполняет назначенные проверки;
- утверждённый scope нельзя менять без разрешения;
- ZAP, фаззер и Dojo подключаются как security consumer-профиль.

### Ролевая поправка

Не превращать `admin_service` в главного администратора всего:

```text
admin_service
  → здоровье коробки, сервисы, retention, vault, диагностика

org_admin / space_admin
  → пользователи, spaces, memberships, проекты

admin_sec
  → security registry, templates, assignments, policies

sec_expert
  → исполнение и анализ проверок
```

Если на первом шаге не хочется добавлять отдельную роль `space_admin`, её права можно временно дать `admin_service`, но capability-блоки нужно оставить разделёнными. Иначе инфраструктурный админ получит доступ к бизнес-содержимому проектов.

## Панели после инженерной ревизии

### Control Panel

Зона `admin_service`: здоровье коробки, сервисы, retention, vault, диагностика. Она может показывать сводку по Spaces, но не должна автоматически раскрывать содержимое всех проектов.

### SecOps Control

Зона `admin_sec`: security registry, templates, assignments, policies и security scope конкретного Space.

### Dashboard

Кросс-продуктовая и кросс-space поверхность результатов с серверной фильтрацией по доступам. Это не «админка третьего уровня», а отдельный read/triage experience.

## Инженерная последовательность PoC

### PoC-0 — общий runtime

```text
один сценарный контракт
        ↓
один runner
        ├── Automation Run
        └── Security Run
```

Доказать, что два режима используют один DSL/Wired/Actions contract, а Automation не требует security-инфраструктуры.

### PoC-1 — минимальная иерархия

Создать в тестовом контуре:

```text
1 Organization
2 Spaces
2 Projects
2 Scenario/Check
2 Runs
```

### PoC-2 — различие workflow

- Automation: пользователь создаёт сценарий сам.
- Security: `admin_sec` создаёт template/assignment, эксперт выполняет.

### PoC-3 — Dashboard visibility

- `admin_service` видит инфраструктурную сводку;
- `space_admin` видит свой Space;
- `admin_sec` видит security-объём своего Space;
- эксперт видит назначенные проверки и разрешённые проекты;
- API отфильтровывает данные на сервере.

Только после этого выбирать готовый admin UI engine и строить оболочки.

## Решение Luna

```text
Installation / Box
└── Organization
    └── Space
        └── Project
            ├── Scenario / Check
            ├── Suite / Plan
            ├── Assignment
            └── Run
                └── Artifacts
```

Продуктовые правила:

```text
Automation Lab
  = user-driven, без обязательных assignments

SecOps Lab
  = admin-governed, templates + assignments + policies

Оба
  = один Browser Core, один DSL/Wired, один runner
```

До дополнительной проверки не фиксировать как факты:

- точную внутреннюю иерархию aqua;
- что у конкурентов абсолютно нет templates/assignments;
- необходимость parent-child tree из пяти уровней;
- необходимость дать `admin_service` весь бизнес-доступ;
- что Blank обязан быть отдельным типом Check.

**Рекомендация:** сначала утвердить канонические сущности и права, потом выбирать дорогой admin engine. UI-шаблон не должен диктовать модель продукта.

## Раунд Gemini: продуктовый дизайн, эргономика и пользовательский путь

> **Голова:** Gemini 3.7 Flash · Product Design & Customer Experience · Mountain View · 23 августа 2026.
> Цель раунда — превратить архитектурные сущности Luna (`Org → Space → Project → Assignment → Run`) в живой, тактильно приятный и понятный интерфейс без когнитивной перегрузки.

### 1. Навигация и ментальная модель: паттерн Linear / Supabase

Пользователь не должен думать об иерархии таблиц в БД. Навигация строится через **Top-Bar Scope Picker** и контекстный сайдбар:

```text
┌────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│  [ 🏢 Сбербанк ]  /  [ 🛡️ Департамент ИБ ▾ ]  /  [ 📁 Проекты ▾ ]            🔍 Cmd+K   🔔 (2)  👤 Alex │
├────────────────────────┬───────────────────────────────────────────────────────────────────────────────┤
│ 🛡️ SECOPS SPACE        │  PROJECTS & ASSIGNMENTS                                 [ + New Project ]     │
│                        │                                                                               │
│ 📊 Dashboard           │  📌 My Assigned Queue (2)                                                     │
│ 🎯 Targets Registry    │  ┌─────────────────────────────────────────────────────────────────────────┐  │
│ 📋 Blank Assignments   │  │ ⏳ Q3 DAST Audit: Internet Banking    Due: 28 Aug    Assignee: Alex (You)│  │
│ 📁 Projects            │  │    Target: https://ib.sber.ru  ·  Policy: PCI-DSS Strict  ·  [ Open → ] │  │
│ 🛡️ Security Policies   │  └─────────────────────────────────────────────────────────────────────────┘  │
│ 👥 Space Team          │                                                                               │
│ ⚙️ Space Settings      │  📁 All Space Projects                                                        │
│                        │  • 🛒 Retail E-Commerce (14 runs · 🟢 clean)                                  │
│ ────────────────────── │  • 💳 Payment Gateway API (42 runs · 🔴 2 High)                               │
│ ⚙️ Machine Room (Box)  │  • 📱 Mobile Backend Auth (5 runs · 🟡 1 Med)                                  │
└────────────────────────┴───────────────────────────────────────────────────────────────────────────────┘
```

#### Ключевые UX-решения навигации:
1. **Space Switcher в хедере:** выпадающий список доступных пространств («Департамент ИБ», «QA Розница», «Мобилка»). Если у пользователя доступ только в один Space — дропдаун превращается в статичный бейдж.
2. **Command+K Quick Jump:** мгновенный поиск по проектам, сценариям, таргетам и упавшим прогонам за 2 нажатия клавиш.
3. **Разделение уровней доступа в сайдбаре:**
   - Обычный инженер видит только рабочие разделы своего Space.
   - Пункт `⚙️ Machine Room (Box)` внизу сайдбара виден **только** пользователю с ролью `admin_service`. Никаких путаниц с инфраструктурными настройками.

### 2. Четыре пользовательские персоны и их рабочие экраны

| Персона / Роль | Главный экран | Что видит и делает | Визуальный тон |
|---|---|---|---|
| **Инфра-админ** (`admin_service`) | `#/control` (Machine Room) | Телеметрия контейнеров, здоровье ZAP/Live/Allure, ползунки Retention, Vault, список Spaces и выделенные квоты. Ноль шума от тестов. | Строгий темный slate/zinc, моноширинные метрики, графики нагрузки. |
| **Лид ИБ / Space Admin** (`admin_sec`) | `#/spaces/:id/admin` (Control Deck) | Реестр веб-приложений, выдача болванок (Assignments), матрица политик гейтов, команда домена. | Defense-grade: акценты amber/crimson, щиты, статусы комплаенса. |
| **Сек-эксперт / QA** (`sec_expert` / `qa_engineer`) | `#/spaces/:id/projects` (Studio Canvas) | «Моя очередь задач», редактор графа сценариев, живой раннер, логи шагов, инспектор локаторов. | Творческий студийный: чистый холст, цветные pill-ноды, плавные связки. |
| **Стейкхолдер / Аудитор** (`user` / `viewer`) | `#/spaces/:id/dashboard` (Executive Summary) | Тренды прогонов, тепловая карта уязвимостей, экспорт отчетов (PDF / Allure), статус релизных гейтов. | Презентационный: крупные KPI-карточки, понятные графики, минимум кнопок действия. |

### 3. UX-сценарий выдачи и выполнения болванки (Blank Assignment Flow)

Разделение Luna (`Check` отдельно от `Assignment`) дает идеальный пользовательский опыт:

```text
ШАГ 1: Лид ИБ нарезает задачу (30 секунд)
┌─────────────────────────────────────────────────────────────┐
│  📋 Issue Security Assignment                               │
│                                                             │
│  Target App:     [ 🛒 Internet Bank (ib.sber.ru)        ▼ ] │
│  Security Scope: [ Tier-1 (Full DAST + Fuzz + Spider)   ▼ ] │
│  Gate Policy:    [ PCI-DSS Strict (0 High, Max 2 Med)   ▼ ] │
│  Assign To:      [ 👤 Alex (Senior Sec Expert)          ▼ ] │
│  Due Date:       [ 📅 28 August 2026                    ▼ ] │
│                                                             │
│  [ Cancel ]                             [ 🚀 Issue Blank ]  │
└─────────────────────────────────────────────────────────────┘
                             ↓
ШАГ 2: Эксперт Alex открывает задачу в 1 клик
┌─────────────────────────────────────────────────────────────┐
│  🔔 Уведомление: «Вам назначена проверка ib.sber.ru»        │
│  Кнопка: [ Open in Canvas → ]                               │
└─────────────────────────────────────────────────────────────┘
                             ↓
ШАГ 3: Холст открывается с готовыми защитными рамками!
┌─────────────────────────────────────────────────────────────┐
│  CANVAS: Q3 DAST Audit (ib.sber.ru)                         │
│                                                             │
│  [🔒 Lock Target: https://ib.sber.ru] (залочено админом)    │
│        ↓                                                    │
│  [ ➕ Пустой слот: Добавьте Auth Flow ]                      │
│        ↓                                                    │
│  [ ➕ Пустой слот: Добавьте Business Logic Scenario ]       │
│        ↓                                                    │
│  [🔒 Policy Gate: PCI-DSS Strict] (контролируется админом)  │
└─────────────────────────────────────────────────────────────┘
```

**В чем кайф этого UX:**
- Эксперт не тратит время на согласование таргета и политик — они уже зафиксированы в болванке.
- Эксперт фокусируется на своем мастерстве: накликивает шаги авторизации и бизнес-логику в слоты.
- Нельзя случайно натравить сканер на чужой хост: целевой URL залочен администратором.

### 5. URL-схема фронтенда (чистый роутинг без конфликтов)

```text
#/control                                → Machine Room (admin_service)
#/spaces                                 → Выбор пространства
#/spaces/:spaceId/dashboard              → Сводка результатов Space
#/spaces/:spaceId/projects               → Список проектов (Automation или Security)
#/spaces/:spaceId/projects/:projId       → Студия / Canvas сценария
#/spaces/:spaceId/admin                  → SecOps Control (болванки, таргеты, политики)
#/spaces/:spaceId/runs/:runId            → Детальный отчет конкретного прогона
```

### Резюме Gemini

1. **Space Switcher (Linear-style)** решает всю иерархию в 1 элементе интерфейса.
2. **Blank Assignment** превращается из абстрактной концепции в понятный 3-шаговый flow: Админ нарезал → Эксперт нажал кнопку → Холст открылся с залоченным таргетом.
3. **Разделение визуального языка** между Automation Lab (легкий Cyan DevTools) и SecOps Lab (строгий Shield Enterprise) подчеркивает разницу в цене и ценности для клиента.
4. **Machine Room (`#/control`)** изолирован от проектов, избавляя инженеров от системного мусора, а сисадмина — от чужих тестов.
