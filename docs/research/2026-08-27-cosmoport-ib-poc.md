## 0. Что уже есть в Cosmoport (и почему этого недостаточно)

У банка в портале Cosmoport уже работает автоматический ZAP CI:

```text
разработчик →
  портал → кнопка «Запустить» →
  GitLab CI → zap_universal_ci →
  SARIF → AppSecHub
```

Это **одноразовый неподписанный прогон**:

- ZAP в режиме baseline/active scan;
- без авторизации (или с примитивным токеном);
- без оператора — результат падает в реестр находок;
- один отчёт — SARIF;
- никакой доказательной базы, кроме alert reference.

**Чего нет:**

- Целенаправленного фаззинга по словарям корпуса;
- Авторизованного браузерного прохода (login → сессия → действия);
- Живого наблюдения за атакой;
- Полной evidence chain (скриншот → запрос → ответ → ZAP-алерт → тайминг);
- ГОСТ-овского Акта с логотипом ЦБ;
- Ролевого разделения: кто назначил проверку, кто выполнил, кто утвердил.

## 1. Сценарий PoC: рабочий день Эксперта ИБ

### 1.1. Утро: получение задания

```text
Администратор ИБ (admin_sec) в PrettyK:
  → открывает лесенку Cosmoport
  → выбирает приложение: «Платёжный хаб» (payment-hub)
  → выбирает сборку: v2.1.0 (stage)
  → URL деплоя подтягивается автоматически
  → нарезает болванку проверки: «Плановая, pre_release»
  → назначает исполнителя: Эксперт ИБ Петров
```

### 1.2. День: исполнение проверки

```text
Эксперт ИБ (sec_expert) в PrettyK:
  → видит болванку в своём списке
  → проверяет авторизацию (auth-модуль: login → сессия)
  → запускает прогон

PrettyK выполняет:
  → Playwright: авторизованный браузерный проход
  → Fuzzer: словари SQLi, XSS, command injection, path traversal
  → ZAP: перехват трафика, пассивное и активное сканирование
  → Live: оператор видит шаги, алерты и evidence в реальном времени

Оператор наблюдает:
  → шаг 04: Fuzzer отправляет ' OR 1=1-- → 500 Internal Server Error
  → ZAP: High alert «SQL Injection» на /api/users
  → Evidence: скриншот ответа, RAW request/response, тайминг 183ms
  → оператор ставит маркер «Критическая находка»
```

### 1.3. Вечер: оформление результата

```text
Эксперт ИБ завершает проверку:
  → PrettyK формирует Акт в ГОСТ-формате
  → логотип ЦБ в шапке, нормы 683-П / 757-П / ГОСТ Р 57580.1
  → таблица находок с уровнем риска и evidence-ссылками
  → подписи: Исполнитель __________ / Проверил __________

Администратор ИБ утверждает Акт:
  → admission gate пройден
  → результаты дублируются в AppSecHub портала Cosmoport
  → Акт сохраняется в реестр деплоев (deployStore)
```

## 2. Что конкретно тащим в коробку

### 2.1. Лесенка ЖЦ Cosmoport: app → build → deploy → URL

**Что уже есть:** mock (2 приложения, 3 builds, 3 deploys).

**Что нужно для PoC:** та же модель, но оператор реально видит и выбирает цель.

```text
[ Выбор приложения ▼ ]  ← из Cosmoport (mock → live API когда портал даст)
[ Выбор сборки    ▼ ]  ← builds[]
[ Выбор деплоя    ▼ ]  ← deploys[] → URL автозаполнен
```

Оператор не вводит URL руками. Выбрал знакомое приложение из портала — всё подтянулось.

### 2.2. Ролевая модель банка в действии

| Роль в Cosmoport | Роль в PrettyK | Что делает в PoC |
|---|---|---|
| Администратор ИБ | `admin_sec` | Нарезает болванки, назначает исполнителей, утверждает Акты |
| НШР (админ портала) | `admin_abnormal` | Внештатные проверки (emergency) |
| Эксперт ИБ | `sec_expert` | Исполняет проверки из болванок, ставит маркеры находок |

### 2.3. Бланки ТЗ и Акта (ГОСТ)

**Что уже есть:** `cbr-specific/` (локально, не в git) — бланки, profile.ts с нормами, letterhead логотипа ЦБ, пример ТЗ (385 строк HTML), пример Акта.

**Что нужно для PoC:** PrettyK формирует эти документы **автоматически** по результатам прогона:

```text
ТЗ (до проверки):
  → объект проверки (из лесенки: app/build/deploy)
  → методика (из манифеста: шаги, словари, auth-профиль)
  → нормативная база (profile.ts: 683-П, 757-П, ГОСТ Р 57580.1)
  → контур испытаний («Внутренняя сеть ПлЦР ЦБ РФ»)

Акт (после проверки):
  → дата и время прогона
  → таблица находок (severity, evidence-ссылки, рекомендации)
  → заключение о допуске (admission gate)
  → подписи: Исполнитель / Проверил
```

### 2.4. Интеграция с AppSecHub портала

После прогона PrettyK отдаёт находки в формате, который Cosmoport может потребить:

```text
run_id / project_id
  → finding[]
    → severity
    → title
    → description
    → evidence references
    → CWE / OWASP category
```

Не вместо SARIF из CI. **Дополнительно к SARIF** — потому что это другая методика (операторская, а не автоматическая).

## 3. Почему это не «ещё один ZAP»

| | ZAP CI в Cosmoport | PrettyK в Cosmoport |
|---|---|---|
| **Кто запускает** | Разработчик (кнопка в CI) | Эксперт ИБ (осознанно) |
| **Метод** | Автоматический active/passive scan | Fuzzer по словарям + Playwright browser |
| **Авторизация** | Токен или её нет | Auth-модуль: login → сессия → DOM |
| **Наблюдение** | Нет (ждём SARIF) | Live: шаги, алерты, evidence в реальном времени |
| **Evidence** | ZAP alert reference | Скриншот + RAW request/response + тайминг + trace |
| **Отчёт** | SARIF (машинный) | ГОСТ Акт (человеческий, с логотипом ЦБ) |
| **Роли** | Нет (кто нажал кнопку) | Администратор ИБ → Эксперт ИБ → утверждение |
| **Scope** | Одно приложение, один тип сканирования | Комплекс: браузер + API + фаззинг + ZAP одновременно |

**Вывод для банка:**

> ZAP CI отвечает на вопрос «есть ли уязвимости в коде».  
> PrettyK отвечает на вопрос «пройдёт ли приложение приёмку ИБ».

Это разные классы проверки. Одно не заменяет другое.

## 4. Минимальный PoC (что реально показать)

### Неделя 1: лесенка + автозаполнение

- Оператор логинится под `sec_expert@spaceport.cbr.ru`
- Видит лесенку Cosmoport (mock или live)
- Выбирает приложение → сборку → деплой → URL в форме автозаполнен
- Кнопка `▶ Run` активна

### Неделя 2: прогон с живым наблюдением

- PrettyK выполняет прогон: Playwright browser + Fuzzer + ZAP
- Studio переходит в Execution View
- Оператор видит: шаги, алерты, evidence
- По окончании: summary с находками

### Неделя 3: Акт и интеграция

- PrettyK формирует Акт (HTML) с логотипом ЦБ и таблицей находок
- Результаты сохраняются в deployStore с привязкой к project_id
- Формируется payload для AppSecHub (JSON)

## 5. Границы PoC (чего не делаем)

- **Не** требуем живой API портала (mock достаточен для демо).
- **Не** интегрируемся в GitLab CI портала (это орг. вопрос, не технический).
- **Не** брендируем PrettyK под ЦБ (коробка остаётся коробкой, пак — паком).
- **Не** даём порталу управлять коробкой (коробка управляет собой, портал только даёт лесенку).
- **Не** коммитим CBR-пакет (`cbr-specific/`) в git.
- **Не** делаем второй продукт — это пак `cosmo-custom` поверх коробки `prettyk-pure`.

## 6. Бонус: живой показ для лица, принимающего решение

**Сценарий для демо:**

```text
1. Открываем PrettyK. Видим лесенку: «Платёжный хаб v2.1.0 (stage)».
2. Нажимаем Run.
3. На экране:
   → браузер заходит на форму логина, вводит креды
   → фаззер отправляет векторы SQLi
   → ZAP ловит 500-й ответ
   → на экране загорается красный маркер «SQL Injection — CRITICAL»
   → оператор кликает → evidence: скриншот ошибки, RAW SQL-вектор, response body
4. Прогон завершён.
5. Нажимаем «Сформировать Акт» → открывается HTML с логотипом ЦБ,
   таблицей находок и ГОСТ-формулировками.
6. Администратор ИБ ставит admission gate: «Допуск не пройден — требуется fix».
```

Весь поток — от выбора приложения до ГОСТ-Акта — **в одном окне**, без переключения между порталом, ZAP, браузером и Word.
