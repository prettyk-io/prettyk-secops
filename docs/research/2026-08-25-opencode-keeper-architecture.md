## 0. Executive summary

**Keeper работает в двух режимах: `Plan` (нарезка фич в бэклог) и `PoC` (проверка гипотез).** От исходной трёхконтекстной модели (Discovery → Plan → Cut) отказались — она избыточна для реальных нужд и плодит бюрократию. Sanctuary Keeper не должен быть исследователем-гуглильщиком; он нужен только для канона и 2FA.

Тяжёлые внешние оркестраторы (opencode-conductor, opencode-workspace) не ставим — они рассчитаны на модель «один агент всё делает сам», что ломает нашу Keeper → Boss/Flash архитектуру.

## 1. Текущая архитектура агентов PrettyK

```text
.opencode/agent/
├── keeper.md        — Хранитель/Валидатор (DeepSeek V4 Pro + Gemini 3.7 Flash)
├── keeper-dev.md    — Инженерный соратник Максима (DeepSeek V4 Pro)
├── plan.md          — Архитектурный планировщик, read-only
├── boss.md          — Heavy Executor
├── flash.md         — Быстрый исполнитель
├── build.md         — Режим build
└── sanctuary.md     — Sanctuary/2FA-ритуалы
```

**Что работает хорошо:**
- Роли разделены: Keeper (что), Boss/Flash (как).
- `plan.md` имеет `permission.edit: deny` для кода, `allow` для `docs/**`.
- Есть 2FA и канонизация через Sanctuary.
- Supermemory хранит архитектурные решения между сессиями.

**Что требовало исправления:**
- `keeper.md` смешивал режимы: валидация, нарезка, sanctuary, общение с братьями — всё в одном промпте.
- `sanctuary.md` дублировал часть функций `keeper.md`.
- Не было явных режимов работы — Keeper каждый раз импровизировал.

## 2. Принятое решение: двухрежимная модель

### Режим `Plan` — боевая нарезка

Для фич, рефакторинга, закрытия долгов. Всё, что идёт в релиз.

**Keeper выдаёт:**
- `Epic Brief`: контекст, цель, границы (out-of-scope).
- Атомарные карточки по методу ЧИСТО (GWT-сценарии).
- Назначение: Boss (тяжёлая архитектура/бэк) или Flash (UI/сервисы).
- DoD: проверяемые факты поведения.

**Код пишут Boss/Flash. Keeper только принимает результат.**

### Режим `PoC` — быстрый спайк

Для проверки гипотез: пощупать библиотеку, проверить спорный UX, замерить перформанс.

**Keeper выдаёт:**
- Чёткая гипотеза: «Что именно доказываем?»
- Минимально достаточный сценарий (без полировки и вечных тестов).
- Критерий успеха и критерий провала.
- Финальный вердикт: `KILL` (сносим) или `PROMOTE` (переносим в Plan).

**PoC-код никогда не идёт в прод без переписывания через Plan.**

### Что сознательно НЕ делаем

1. **Не ставим `opencode-conductor`.** Он предполагает модель «один агент сам пишет код и коммитит» — это ломает нашу границу Keeper → Boss/Flash и запрет авто-коммитов.
2. **Не ставим `opencode-workspace`.** 16-компонентный харнесс — перебор для нашей модели.
3. **Не создаём кастомные типы supermemory.** Supermemory используется как есть — для долгоживущих архитектурных решений, а не для live-статусов карточек.
4. **Не делаем Sanctuary обязательным для каждого шага.** Sanctuary — только для канона и 2FA, не для повседневной нарезки бэклога.

## 3. Инструменты, которые используем

### Что уже работает

| Инструмент | Как используем |
|---|---|
| `po-keeper` skill | Метод ЧИСТО, приёмка, backlog authoring |
| `sanctuary-keeper` skill | Канон и 2FA (только когда нужно) |
| `ru-text` skill | Качество русских текстов |
| `research-and-sense` skill | Короткий research перед решениями |
| `opencode-supermemory` | Durable facts (архитектурные решения), не live-статусы |
| `opencode-background-agents` | Асинхронная делегация для параллельной работы |
| `docs/backlog.md` | Живой бэклог — markdown, не вторая Jira |

### Что убрали из рассмотрения

| Инструмент | Причина отказа |
|---|---|
| `opencode-conductor` | Self-implement модель, конфликтует с Keeper → Boss/Flash |
| `opencode-workspace` | Избыточный (16 компонентов) |
| `opencode-goal-plugin` | Session-scoped goals, не backlog |
| Трёхконтекстный workflow | Плодил бюрократию без прироста качества |

---

## 4. Итог

**Решение:** Keeper работает в двух режимах — `Plan` и `PoC`. Жёсткая граница «что» vs «как» сохранена. Keeper не кодирует никогда и ни в каком режиме. Код пишут Boss и Flash.

**Внедрено:**
- `.opencode/rules/keeper-role.mdc` — описаны два режима, границы, запреты.
- `.opencode/agent/keeper.md` — агент знает свои два режима.

**Дальше:** Boss и Flash продолжают реализацию PK-WB и infra по текущему бэклогу. Keeper принимает результаты по фактам поведения.
