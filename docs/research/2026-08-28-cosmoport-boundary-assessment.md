## 1. Архитектурная панорама: Три слоя — три разных мира

Главная ошибка ранних концепций Cosmoport 2.0 заключалась в попытке слепить в один монолитный комбайн три фундаментально разные предметные области с разными источниками истины, жизненными циклами и моделями отказов.

```text
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│ 🚀 СЛОЙ 1: DELIVERY PLANE (Контур Сборки и Доставки)                                       │
│ ├─ Субстраты: Git Forge (Gitea/GitLab), CI Runners (Woodpecker/Jenkins), Artifact Registry  │
│ ├─ Задачи: Компиляция кода, SAST, SCA-проверки зависимостей, упаковка OCI-образов, Deploy   │
│ └─ Источник истины: Git Commit SHA + Immutable Artifact Digest (sha256)                     │
└──────────────────────────────────────────────┬──────────────────────────────────────────────┘
                                               │ Release Candidate Ready (Artifacts & Envs)
                                               ▼
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│ 🛰️ СЛОЙ 2: RELEASE CONTROL PLANE / COSMOPORT 2.0 (Орбитальный Диспетчер Релизов)           │
│ ├─ Сущности: Release Candidate, Зоны (Dev→Staging→Prod), Регламенты, RBAC/SoD, Governance    │
│ ├─ Задачи: Принятие решения о промоушене (Promote/Hold/Reject), аудит допусков, подписание │
│ └─ Источник истины: PostgreSQL State Machine + Immutable Release Decisions Ledger           │
└──────────────────────────────────────────────┬──────────────────────────────────────────────┘
                                               │
                                               │ ⚡ Versioned Security Assessment Contract
                                               │    (Запрос: "Проверь этот артефакт в зоне X")
                                               │ ◄──(Ответ: "Вот доказанные findings и вердикт QG")
                                               ▼
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│ 🏰 СЛОЙ 3: PRETTYK SECOPS ENGINE (Суверенное Ядро ИБ-Фаззинга и DAST)                       │
│ ├─ Движки: Playwright CDP, scanner Demon (:8080), PrettyK Fuzzer (:8767), Discovery Engine      │
│ ├─ Управление: Quality Gate (Fail-Closed), Admission Policy, WARZONE Timeline, Studio/Editor│
│ └─ Источник истины: Immutable Evidence Chain (SHA-256 Merkle Ledger + S3 Evidence Storage) │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Разделение властей (Separation of Concerns):
- **Слой 1 (Delivery):** Делает бинарник и выкатывает стенд. Не знает про логику ИБ-допуска.
- **Слой 2 (Cosmoport):** Решает, **куда и когда двигать релиз**. Не знает, как работает фаззер или Playwright.
- **Слой 3 (PrettyK DAST):** **Добывает доказательства и факты уязвимостей**. Не принимает бизнес-решений о релизах.

## 2. Почему жесткая сцепка (Tight Coupling) смертельна для PrettyK Box

### 2.1. Конфликт фундаментальных вопросов
- **PrettyK Box отвечает:** *«Что реально сломано в работающем приложении и чем это доказано (evidence)?»*
- **Cosmoport отвечает:** *«Имеет ли право данный релиз переехать в бой по совокупности согласований, сканов и регламентов?»*

Смешение этих сущностей превращает чистый SecOps-сканер в громоздкий корпоративный комбайн, убивая легковесность, скорость и суверенитет коробки `prettyk-pure`.

### 2.2. Матрица источников истины (Source of Truth)

| Сущность / Факт | Истинный владелец | Доступ для других слоёв |
|---|---|---|
| Исходный код, коммиты, ветки | **Слой 1 (Forge/Git)** | Слой 2 читает метаданные; Слой 3 не знает про Git |
| Релизные кандидаты, стадии, решения о промоушене | **Слой 2 (Cosmoport)** | Слой 1 получает команду на Deploy; Слой 3 не знает про зоны |
| Сессии браузера, атаки, фаззинг, scanner-состояние | **Слой 3 (PrettyK Engine)** | Слой 1 и 2 не имеют прямого доступа к сокетам/сессиям |
| ИБ-уязвимости (Findings), сырые улики (Screenshots/HAR) | **Слой 3 (PrettyK Engine)** | Слой 2 получает только Read-Only Summary + Ссылки на улики |
| Финальный вердикт Quality Gate | **Слой 3 (PrettyK Engine)** | Слой 2 учитывает вердикт во входящих условиях промоушена |
| Решение на ручной оверрайд (IB Sign-off) | **Слой 2 (Cosmoport)** | Слой 3 регистрирует неизменяемый аудит-лог |

Попытка объединить таблицы `cosmo_runs` и `prettyk_runs` в одну БД или общий ORM приведет к катастрофе синхронизации и сделает невозможным запуск PrettyK в airgap без Cosmoport.

### 2.3. Радикальная изоляция зоны поражения (Blast Radius)

```text
       Сбой в Cosmoport 2.0                    Сбой в PrettyK Engine
 (Упал Valkey, зависли воркеры)         (Таймаут scanner, краш браузера цели)
               │                                       │
               ▼                                       ▼
  PrettyK DAST продолжает работать!      Cosmoport получает честный FAIL-CLOSED!
  Studio / Editor функционируют.         Никакого ложного "зелёного" релиза.
  Коробка автономна на 100%.             Релиз замораживается до разбора улик.
```

## 3. Иерархия идентификаторов: Конец путанице `run_id`

В кодовой базе возникла опасная терминологическая коллизия: словом `run` называли и запуск сценария в браузере, и CI-пайплайн сборки, и процесс продвижения релиза. 

Каноническая строгая иерархия идентификаторов:

```text
release_id (UUID — Cosmoport: "Релиз биллинга v2.4.0-rc1")
  │
  └── promotion_operation_id (UUID — Cosmoport: "Попытка перемещения Staging → Prod #3")
        │
        ├── delivery_job_id (Woodpecker: "Сборка контейнера и выкатка на стенд")
        │
        └── assessment_request_id (Контракт: "Запрос на аудит безопасности в PrettyK")
              │
              └── secops_execution_run_id (PrettyK: "Прогон DAST + Fuzzing + Playwright")
                    ├── finding_id ("SQLi в /api/v1/auth")
                    └── evidence_artifact_id ("PCAP-дамп + скриншот подтверждения")
```

- **PrettyK Core оперирует исключительно `secops_execution_run_id`**.
- Внешний `assessment_request_id` и `correlation_id` принимаются PrettyK как непрозрачные сквозные метаданные для трассировки и Allure-отчетов.

Взаимодействие между Cosmoport и PrettyK DAST строится исключительно поверх строго типизированного, версионированного REST/JSON и SSE протокола.

  },

### 4.3. Семантика статусов вердикта (Никаких скрытых Pass!)
- `PASSED` — Все атаки завершены, порог уязвимостей соблюден, релиз чист.
- `BLOCKED` — Найдены критические уязвимости, превышающие порог Quality Gate.
- `FAILED` — Инфраструктурный сбой сканера (цель легла, нет сети, таймаут).
- `UNAVAILABLE` — Слой PrettyK перегружен или недоступен.
- `INCOMPLETE` — Сканирование прервано оператором или лимитом времени без достаточных доказательств.

> 🔴 **Железный закон ИБ-допуска:** Любой статус, отличный от `PASSED`, трактуется Cosmoport как **НЕДОПУСК (HOLD/BLOCK)**.

## 7. Дорожная карта и Ворота Приёмки (Quality Gates)

Внедрение Cosmoport 2.0 разбивается на изолированные фазы. Переход между фазами блокируется при несоблюдении критериев.

```text
[Фаза 0: Изоляция и Контракты]
       │
       ▼
 🔴 GATE A: Standalone Pure Box Safety (DAST работает в 1 клик без единого сервиса Cosmoport)
       │
       ▼
[Фаза 1: Независимый Cosmoport Kernel (Mock-адаптеры)]
       │
       ▼
 🔴 GATE B: Contract Verification (Сквозной обмен JSON-запросами между Cosmo и PrettyK по HTTP)
       │
       ▼
[Фаза 2: Реальные Адаптеры Доставки (Gitea + Woodpecker)]
       │
       ▼
 🔴 GATE C: Fail-Closed Acceptance (При падении DAST или тайм-ауте релиз надежно блокируется)
       │
       ▼
[Фаза 3: Полносвязный Steel Thread на живом стенде]
```

### Критерии закрытия Фазы 0 (Прямо сейчас):
1. Никаких новых внешних зависимостей (`fastapi`, `sqlalchemy`, `alembic`) в основном `.venv` PrettyK.
2. `orchestrator/core/controller.py` свободен от импортов Cosmoport.
3. Документ зафиксирован как архитектурный ориентир братства.

## 🏛️ Резюме Хранителя

Мы не повторяем ошибок `scanner-kdt` и старого `cosmoport 1.0`, где всё было сварено в нераспутываемый монолитный суп.

- **PrettyK DAST** — это наше отточенное боевое оружие (меч).
- **Cosmoport 2.0** — это командный пункт генерального штаба (карта и радар).

Меч должен рубить безупречно и автономно, даже если штаб временно потерял связь. Штаб должен отдавать приказы и сверять карту, не пытаясь самостоятельно ковать сталь.

*Границы высечены в камне. Архитектура чиста.*
