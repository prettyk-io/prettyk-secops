# PrettyK SecOps: план возврата рабочей коробки

**Цель владельца:** вернуть проверяемое поведение редактора и запуска, затем подтвердить его прежним рабочим сценарием на локальном OWASP Juice Shop.

> Это план восстановления, не подтверждение готовности и не разрешение запускать массовый скан. Сначала нужен честный Validate/Run-контракт; затем — bounded smoke на локальной цели.

## Что проверено сейчас

- Editor, Playground API, PrettyK Live, Juice Shop, scanner и Allure отвечают/слушают локально. Editor, Juice Shop и scanner health URL вернули HTTP 200. У корня Playground HTTP 404, но его API-маршруты отвечают.
- Juice Shop доступен локально. Selenium Grid `:4444` сейчас не слушает; прежние live-тесты, которые требуют Grid, в таком состоянии не могут дать успешное живое подтверждение. Авторинг-браузер работает в отдельном контейнерном контуре.
- Прямой запрос валидатора с пустой строкой возвращает `ok=true` и пустой список диагностик. С запросом `nonsense_xyz` тот же живой валидатор возвращает ошибку. Следовательно, подтверждён ложноположительный результат для пустого документа; утверждение, что произвольная ахинея проходит валидатор, пока не воспроизведено на чистом API.
- Кнопка общей проверки не выполняет проверку пустоты и не вызывает полную проверку обязательных полей. Она зависит от диагностик редактора и конструктора, собранного из текущего состояния документа.
- Редактор синхронизирует изменения с общей моделью с задержкой около 320 мс. Общая команда Validate не сбрасывает ожидающее изменение перед проверкой; проверка может смотреть на предыдущую версию документа, если вызвана до синхронизации. Это сильная подтверждённая по коду гипотеза для «написал ахинею — всё ОК»; воспроизведение глазами ещё требуется.
- Запуск намеренно блокирует пустую проверку до старта процесса. Если обновлённый текст не попал в общую модель, Run может увидеть старое пустое состояние и не стартовать.
- Текущий статус запуска не доказывает недавний запуск: он показывает завершённый старый прогон с ненулевым кодом выхода и путями из прежнего имени репозитория. PrettyK Live сообщает `idle` и старый результат с gate `fail`. Новый run не наблюдался.
- Текущий Juice Shop Wired baseline не проходит validate-only: найдено 5 ошибок в старых шагах/локаторах. Операторская acceptance-fixture отсутствует; соответствующий тестовый файл пропускает оба теста. Значит, сейчас нет работающего автоматического baseline-гейта, который доказывает готовность цепочки.
- В рабочем дереве много незакоммиченных изменений Потока 7 в backend, FE, тестах и compose; там же уже появились worker reports без Keeper-приёмки. Эти изменения не трогать, не stash, не чистить и не переписывать «заодно». Последний коммит — `7d3f242`.

## Приоритеты восстановления

### P0 — Validate проверяет именно текущий документ и никогда не выдаёт ложный зелёный

**Результат для оператора:** пустое содержимое явно помечено как пустое/непроверенное; некорректный шаг получает ошибку с местом; проверка не может пройти по устаревшей версии текста.

**Приёмка:**
- Given пустой документ, When оператор нажимает Validate, Then результат не зелёный и прямо говорит, что проверять нечего.
- Given неизвестный шаг, When оператор сразу после ввода нажимает Validate, Then проверяется именно видимый текст и возвращается ошибка; валидный прежний текст не маскирует новую ошибку.
- Given недоступный backend-валидатор, When оператор нажимает Validate, Then UI показывает «проверка недоступна» или достоверный полный локальный отказ; молчаливый успех запрещён.
- Given сценарий с ошибками в DSL или обязательных настройках, When проверка завершается, Then те же ошибки блокируют и запуск.
- Один и тот же документ и результат видны после перехода между Studio и Editor; ожидающие изменения не теряются и не отстают от редактора.

### P0 — Run либо реально выполняет сценарий, либо сообщает точную причину блокировки

**Результат для оператора:** нажатие Run создаёт один свежий прогон, который видимо проходит состояние «стартовал → выполняется → завершился» и оставляет результат; отказ до старта объяснён и не выглядит как тихое бездействие.

**Приёмка:**
- Given пустой/невалидный сценарий, When оператор запускает Run, Then новый run не создаётся, старая история/артефакты не выдаются за новый результат, причина блокировки видна.
- Given валидный сценарий, When оператор запускает Run, Then создаётся новый идентификатор, процесс действительно исполняет шаги и завершается с фактическим исходом.
- Given завершённый run, Then статус и результат относятся к его свежему идентификатору, а не к оставшемуся в хранилище старому запуску.
- На неуспехе видны причина, лог и доступные evidence; один только HTTP-ответ «started» не считается доказательством выполнения.

### P1 — Вернуть воспроизводимый Juice Shop baseline

**Результат для команды:** есть поддерживаемый локальный baseline, который проходит проверку перед запуском и после запуска доказывает реальное выполнение, а не только синтаксическую валидность или мок.

**Порядок приёмки:**
1. Восстановить sanitized acceptance scenario, согласованный с текущим языком и текущим браузерным runtime; добавить отрицательный вариант с намеренно неизвестным шагом.
2. Прогнать validate-only: позитивный fixture проходит, негативный гарантированно падает.
3. Прогнать ограниченный live smoke на локальном Juice Shop: как минимум открыть целевую страницу, исполнить один заранее ожидаемый сценарный шаг, получить свежий run status и результат/evidence.
4. Затем прогнать прежний полноценный Juice Shop DAST/fuzz набор с ограниченным временем и явным локальным target. Зафиксировать фактический код завершения, findings и артефакты; для уязвимой цели gate-fail может быть ожидаемым, но «ничего не исполнилось» — нет.
5. Явный запуск live-приёмки не должен становиться зелёным из-за skip при недоступной цели/рантайме. Обычная CI-сборка может пропускать live-контур с ясной причиной.

## Очерёдность и разбиение труда

1. **SERIAL — диагностика и P0 Validate/Run:** один владелец end-to-end пути, без параллельного редактирования общей модели документа. Рекомендуемый исполнитель — Boss; сначала сверить его текущий статус и не пересекаться с незакоммиченным WIP Потока 7.
2. **SERIAL — восстановление baseline:** после зелёных негативных/позитивных проверок Validate и Run зафиксировать минимальный стабильный Juice scenario и его контракт с target/runtime.
3. **SERIAL — живой smoke → полноценный DAST/fuzz:** smoke сначала, расширенный набор только если свежий run доказывает фактическое исполнение и выдаёт артефакты.
4. Keeper проверяет поведение на стенде; после этого возвращаемся к оставшимся карточкам Потока 7. Не распараллеливать сейчас трёх исполнителей на общий Validate/Run путь.

## Ограничения и риски

- Цель теста — только локальный Juice Shop; не направлять baseline на внешний/production target.
- Не очищать Juice Shop во время живого прогона: его пересоздание сбрасывает состояние цели.
- Ненулевой quality-gate на намеренно уязвимой цели сам по себе не означает, что выполнение сломано. Разделять «шаги исполнились», «артефакты получены» и «security gate прошёл».
- Не объявлять коробку восстановленной по unit-тестам, мокам, успешному HTTP `started` или пропущенным live-тестам. Нужен один свежий наблюдаемый live-run.

## Стоп-критерий эпика

Максим может в текущей версии редактора: ввести заведомо неверный шаг и получить отказ; запустить валидный Juice Shop scenario и увидеть свежий run, реальные шаги, фактический финальный исход и evidence. После этого можно говорить о возвращении работоспособности.
