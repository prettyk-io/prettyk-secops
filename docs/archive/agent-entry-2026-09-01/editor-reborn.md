# Editor Reborn — стратегия натяжки Workbench до продукта

> **Статус:** `DRAFT / evolve` — рабочая стратегия, не CANON и не обещание релиза.
> **Дата среза:** 25 августа 2026.
> **Владелец решения:** Максим.
> **Роль документа:** зафиксировать правду о новом Editor, не дать похоронить старый Explorer и разложить адаптацию уже написанных эпиков на проверяемые поведенческие шаги.

---

## 0. Что сказал заказчик

> «Там на двоих пилить можно? Давай если не выгодно на 2го нарежем другое отдельно что-то а сами пойдем эдитор натягивать который они сделали. Только перед этим скажи, эти обезьяны explorer мне мой туда окучили или забили хуй еще пока? Это надо продумывать. я вот тебе скрин 1 приложил. Это старый Editor. В него пиздец времени и сил вложено. Особенно в Explorer. Скрин 2 это только само по себе вот подгонка этих линий заняла 3-4 часа. Пиздец нахуй брат. Давай планировать нормально. Пиши документ editor-reborn.md и нашу стратегию как мы эти написаные макаками эпики щас будем растягивать.»

Это не просьба «нарисовать ещё одну панель». Интент — получить рабочий Editor, в котором новый Workbench не отменяет накопленный продуктовый опыт и не заставляет оператора заново учиться навигации.

## 1. Вердикт Keeper — коротко и без лака

**Старый Explorer в новый Editor surface не перенесён.**

Новый Workbench получил каркас: панели, Monaco, draft, commit/diff, Browser Stage, debugger, language intelligence и связанные контуры. Но его левый Explorer в контролируемом режиме сейчас является плоским списком доступных DSL-вкладок. Это не тот семантический Explorer, который был сделан и вылизан в старом Editor.

При этом старый Explorer не выброшен полностью:

- богатая реализация всё ещё живёт в Studio и её внутреннем Editor mode;
- общий контур данных между поверхностями существует;
- старые корни, папки, действия, иконки и геометрия в репозитории присутствуют.

Итоговая формула:

> **PK-WB foundation closed ≠ Editor product closed.**

Поэтому сейчас нельзя честно сказать «Editor готов». Честно можно сказать: **фундамент Workbench сдан, а Editor Reborn — следующий интеграционный эпик**.

### Что именно проверено

Аудит исходников показал следующее:

| Область | Что есть сейчас | Оценка |
|---|---|---|
| Новый Editor surface | Трёхпанельный Workbench с центром редактора и правыми рабочими зонами | Есть каркас |
| Левый Explorer нового surface | Плоский список редактируемых вкладок; standalone-режим содержит mock-строки | **Не parity** |
| Старый/product Explorer | Шесть семантических корней, папки, выбор, переименование, удаление, создание, drag/drop, контекстные действия | Есть, но в другом входе |
| Состояние дерева | В старом Explorer есть запоминание раскрытия и порядок; в новом Workbench это не покрыто | **Разрыв** |
| Визуальный язык | Старые rails/guides, chevrons, spacing и dark/light assets существуют | Нужно перенести без самодеятельного упрощения |
| Связь поверхностей | Studio показывает богатое дерево; новый Editor его обходит | **Главный пользовательский разрыв** |

Иными словами, «макаки» не забили на Explorer целиком, но в новый вход его не окучили. Они поставили на его место слот-заглушку. Это надо исправлять не рисованием поверх заглушки, а возвратом единого поведения.

## 2. Цель Editor Reborn

Оператор открывает один и тот же CheckWorkspace в Studio или Editor и получает одну и ту же рабочую модель:

1. видит знакомый Explorer с теми же семантическими разделами;
2. находит сущность по дереву, папке, поиску или команде;
3. открывает её в редакторе без потери контекста;
4. правит DSL, видит draft/dirty-состояние и сохраняет безопасно;
5. запускает, отлаживает и связывает строку DSL с результатом и evidence;
6. переключает поверхность и возвращается ровно к той сущности и состоянию, с которыми работал;
7. не теряет данные, не получает тихой перезаписи и не видит plaintext-секреты.

Главный принцип: **новые возможности Workbench натягиваются на существующую продуктовую навигацию, а не заменяют её упрощённым списком.**

## 3. Принципы, которые нельзя нарушить

### 3.1. Один Explorer, не два конкурирующих

Нельзя поддерживать два дерева с разными правилами, названиями, состояниями и наборами действий. Пользователь не должен думать, почему в Studio сущность есть, а в Editor она исчезла.

Поверхности могут выглядеть по-разному, но семантика должна быть одной: одни корни, одни сущности, одни правила выбора, открытия и изменения.

### 3.2. Старый визуальный труд — часть продукта

Линии, отступы, chevrons, высота строк, иконки, выделение, dark/light-варианты — не «косметика после функционала». Они являются частью узнаваемости и читаемости дерева. Особенно это относится к guide rails: ручная подгонка в старом Explorer была продуктовой работой, а не случайным CSS.

### 3.3. Foundation не маскирует интеграционный долг

Закрытые карточки PK-WB принимаются по их фактам. Но наличие Monaco, diff и Browser Stage не доказывает, что оператор может пользоваться Editor как прежним рабочим местом.

### 3.4. Сначала поведение, затем параллельная полировка

Boss и Flash могут работать одновременно только по разным контрактам. Два исполнителя не должны независимо «чинить Explorer» и потом склеивать несовместимые деревья.

### 3.5. Никакого расширения scope ради ощущения прогресса

Editor Reborn не должен превращаться в новый rewrite, новый DSL или бесконечную переделку всего Studio. Сначала возвращаем parity, затем аккуратно подключаем уже закрытые возможности Workbench.

## 4. Целевой пользовательский путь

### Happy path

**Given** у workspace есть страницы, сценарии, фаззеры, модули данных, коннекторы и профили аутентификации.

**When** оператор открывает новый Editor, раскрывает раздел, выбирает сущность и вносит изменение.

**Then** он видит знакомую иерархию, открывает выбранный документ в Monaco, видит честный dirty-индикатор, может сохранить, зафиксировать версию, запустить и перейти к результату.

### Переключение Studio ↔ Editor

**Given** оператор находится на выбранной сущности и имеет несохранённые изменения.

**When** он переключает поверхность.

**Then** система не теряет изменения, показывает dirty-guard при необходимости, сохраняет выбранную сущность и продолжает работу в том же workspace.

### Пустой workspace

**Given** в workspace нет сущностей.

**When** открыт Explorer.

**Then** видны все нужные семантические разделы, понятные empty-states и доступное действие создания; пустой список не выдаётся за поломку или отсутствие Editor.

### Отрицательные сценарии

- При конфликте версии оператор видит конфликт и варианты решения; тихой перезаписи нет.
- При ошибке загрузки или сохранения Explorer не показывает устаревшее состояние как подтверждённое.
- При удалении есть явное подтверждение, а отмена оставляет сущность и выбор на месте.
- Секреты не появляются в дереве, подсказках, кеше, DOM или diff в открытом виде.
- Неизвестный или устаревший тип сущности получает честное состояние, а не исчезает бесследно.

## 5. Explorer parity matrix

Это не список пожеланий. Это минимальная матрица, по которой Keeper принимает Editor Reborn.

| Контур | Требуемое поведение | Признак готовности |
|---|---|---|
| Семантические корни | Видны `Модели страниц`, `Сценарии`, `Фаззеры`, `Модули данных`, `Коннекторы и Интеграции`, `Профили аутентификации` | Все шесть разделов присутствуют в новом Editor; пустые разделы не ломают дерево |
| Иерархия | Сущности могут находиться в папках там, где это поддерживает продукт | Папка раскрывается/сворачивается, дочерние элементы имеют правильный уровень и порядок |
| Выбор | Активный leaf однозначно виден и синхронизирован с документом | Клик по сущности открывает правильный документ; переключение не меняет чужую вкладку |
| Раскрытие | Состояние раскрытых разделов и папок не скачет при обновлении данных | После reload/переключения сохраняется ожидаемая навигационная позиция |
| Создание | Оператор может начать создание из соответствующего раздела | Новая сущность появляется в правильном месте и открывается для работы |
| Переименование | Переименование доступно из предусмотренного действия | Новое имя отображается в дереве и документе; отмена не портит старое |
| Удаление | Удаление явно подтверждается | Отмена безопасна; подтверждённая сущность исчезает без фантомного выбора |
| Контекстные действия | Набор действий соответствует типу сущности | Нельзя предложить действие, которое для данного типа невозможно |
| Перемещение | Поддержанные перемещения не ломают порядок и принадлежность | После перемещения дерево, документ и reload показывают одно состояние |
| Иконки | Тип сущности различим и не смешивается с декоративным glyph | Dark/light режимы читаемы, ассеты не перепутаны |
| Guide rails | Вертикальные и горизонтальные линии совпадают с уровнями дерева | Нет обрывов, ложных линий и скачков при раскрытии/анимации |
| Клавиатура | Навигация, раскрытие и ключевые действия доступны без мыши | Фокус видим; F2/Delete/Enter/Escape ведут себя предсказуемо |
| Ошибки и статусы | Ошибка/dirty/disabled не теряются из-за нового layout | Оператор понимает, что требует действия и что уже сохранено |
| Поверхности | Studio и Editor показывают одну модель workspace | Переключение не создаёт второе дерево или вторую правду |

## 6. Нарезка Editor Reborn по ЧИСТО

Карточки ниже описывают **результат глазами заказчика**. Имена файлов, компонентов и способов реализации намеренно не являются частью заданий исполнителям.

### ER-0 — Baseline и контракт parity

**Назначение:** Keeper + Boss + Flash, короткий обязательный нулевой шаг.

**Ч — что сказал заказчик:** «Особенно в Explorer ... подгонка этих линий заняла 3–4 часа».

**И — интент:** команда заранее фиксирует, какой Explorer считается продуктовым эталоном, чтобы новый Editor не собрали по памяти и не потеряли старые решения.

**С — сценарии:**

- **Given** есть старый Editor и новый Editor.
- **When** команда проходит матрицу корней, действий, состояний, keyboard-flow и dark/light.
- **Then** по каждому пункту отмечено: parity, gap или out-of-scope; спорные места имеют одно принятое решение.

**Т — DoD:** утверждён parity checklist; есть один список корней и поддерживаемых действий; известны обязательные acceptance screenshots/flows; нет формулировки «сделать как-нибудь похоже».

**О — out-of-scope:** новый дизайн языка, новые типы сущностей, переписывание всего Studio, расширение backend-модели.

### ER-1 — Единый Explorer в новом Editor

**Назначение:** Boss.

**И:** оператор открывает новый Editor и видит ту же предметную навигацию, что и в старом Editor, а не плоский список случайных вкладок.

**Сценарии:**

- **Given** workspace содержит сущности всех поддержанных типов.
- **When** открыт новый Editor.
- **Then** видны шесть семантических корней, правильные leaves, папки и текущий выбор.
- **Given** workspace пуст или часть данных недоступна.
- **When** Explorer загружается.
- **Then** корни и честные empty/error-states сохраняются; отсутствующие данные не превращаются в молчаливое удаление.

**DoD:** parity matrix по семантике проходит; выбор из Explorer и открытый документ всегда совпадают; Studio и Editor используют одну пользовательскую модель; существующие draft/dirty/conflict правила не обходятся.

**О:** не менять DSL-контракт, не вводить новые сущности, не выкидывать Studio Explorer до доказанной замены.

### ER-2 — Навигация и операции над сущностями

**Назначение:** Boss.

**И:** оператор может управлять рабочим деревом привычными безопасными действиями, не теряя контекст документа.

**Сценарии:**

- **Given** оператор выбрал папку или leaf.
- **When** он раскрывает, создаёт, переименовывает, перемещает или удаляет поддержанную сущность.
- **Then** дерево, активный документ, dirty-состояние и сохранённые данные остаются согласованными.
- **Given** удаление или переход затрагивает несохранённые изменения.
- **When** оператор инициирует действие.
- **Then** появляется понятное подтверждение/dirty-guard; отмена ничего не ломает.

**DoD:** операции проходят happy и negative paths; reload сохраняет ожидаемую структуру; нет фантомных вкладок, потерянного выбора и тихой перезаписи.

**О:** не добавлять новые массовые операции, не менять права доступа и серверную модель сверх необходимого для уже существующих действий.

### ER-3 — Визуальная и интеракционная parity

**Назначение:** Flash, после фиксации ER-0; поведение не дублируется.

**И:** новый Editor выглядит и ощущается как продолжение Editor, в который Максим вложил время: читаемая иерархия, правильный ритм, иконки и линии, а не generic sidebar.

**Сценарии:**

- **Given** Explorer имеет корни, папки, leaves и разные состояния раскрытия.
- **When** оператор смотрит на него в dark и light режимах, меняет ширину и раскрывает уровни.
- **Then** rails/guides, отступы, chevrons, иконки, выделение и высота строк остаются читаемыми и не скачут.
- **Given** длинные имена, ошибки, dirty-state или отсутствие данных.
- **When** они показаны в дереве.
- **Then** текст не уничтожает структуру, статус заметен, а layout не разваливается.

**DoD:** визуальный checklist из ER-0 пройден на reference-размерах и узком viewport; dark/light assets читаемы; нет обрывов guide rails и несогласованных иконок; визуальная полировка не меняет семантику действий.

**О:** не менять правила данных, не создавать второй Explorer, не заменять продуктовые иконки случайным набором glyphs без согласования.

### ER-4 — Explorer ↔ Editor ↔ Run continuity

**Назначение:** Boss + Flash на границе ответственности; один владелец каждого поведения.

**И:** оператор из выбранной сущности без потери контекста проходит путь от дерева к DSL, diff, запуску, debugger и evidence.

**Сценарии:**

- **Given** открыт сценарий и есть изменение.
- **When** оператор открывает diff, запускает шаг или переходит к finding/artifact.
- **Then** выбранный документ, строка, статус и Browser Stage относятся к одной сущности и одному workspace.
- **Given** оператор переключает Studio ↔ Editor во время dirty или активного run.
- **When** он подтверждает переход.
- **Then** состояние не раздваивается и не исчезает.

**DoD:** end-to-end flow проходит на одной сущности; diff/run/debug/evidence не открываются «в пустоту»; dirty/conflict/redaction gates остаются рабочими; второй Chromium runtime не возникает.

**О:** не добавлять новый runner, новый pipeline или новый AI-сценарий; используем уже закрытые возможности PK-WB.

### ER-5 — Надёжность, доступность и безопасные состояния

**Назначение:** Boss, с точечной visual-поддержкой Flash.

**И:** при ошибке оператор понимает, что произошло, и не теряет работу; Explorer доступен мышью, клавиатурой и assistive technology.

**Сценарии:**

- **Given** сеть временно недоступна или сохранение конфликтует.
- **When** оператор продолжает работу.
- **Then** система показывает состояние, не притворяется сохранённой и предлагает безопасное действие.
- **Given** в workspace присутствует секрет.
- **When** оператор раскрывает, сохраняет, сравнивает или запускает документ.
- **Then** секрет не показывается в plaintext там, где это запрещено.

**DoD:** проверены loading/empty/error/conflict/dirty states; keyboard focus и названия элементов доступны; секреты не появляются в localStorage, draft, diff и DOM; тесты запускаются точечно по изменённым контурам.

**О:** не проводить общий security rewrite и не менять канонический машинный контракт без отдельного решения.

## 7. Кто что делает и можно ли вдвоём

### Рекомендованное распределение

| Поток | Владелец | Граница результата |
|---|---|---|
| Семантика Explorer, единая модель workspace, выбор, навигация, draft/conflict/security continuity | **Boss** | Editor ведёт себя как один продуктовый workspace, а не как набор вкладок |
| Визуальная parity старого Explorer, rails/guides, spacing, icons, dark/light, responsive polish | **Flash** | Новый Editor выглядит и читается как продолжение старого, без изменения семантики |
| Parity baseline и финальная приёмка | **Keeper** | Ни одна карточка не закрыта по отчёту о коде; закрытие только по наблюдаемому поведению |

### Условие параллельности

Да, **вдвоём пилить выгодно**, но не два независимых Explorer.

Параллельная работа разрешена после ER-0:

1. Boss фиксирует поведенческий контракт и подключает новый Editor к единой модели.
2. Flash берёт ограниченный визуальный слой и проверяет его на живых состояниях, не создавая собственную модель данных.
3. Keeper держит parity matrix и не принимает «похоже» вместо конкретного GWT.

Если ER-0 показывает, что семантика и визуальный слой пока сцеплены так, что два исполнителя будут трогать один и тот же контур, **не надо насильно делить Explorer**. Тогда Boss делает ER-1/ER-2 последовательно, а Flash получает отдельную, независимую задачу по ADM-PURE UI или accessibility/empty-error states с заранее согласованным контрактом.

### Чего не делать

- Не отдавать обоим исполнителям формулировку «натяните Explorer».
- Не клонировать старое дерево в новый каталог с последующим ручным расхождением.
- Не считать CSS-only карточку заменой отсутствующего поведения.
- Не начинать ADM-PURE как будто Editor Reborn уже закрыт.

## 8. ADM-PURE: параллелить или придержать

Текущий backlog называет ADM-PURE `READY`, 17h, Boss, и одновременно в верхней таблице оставляет противоречивый `ACTIVE`. Это надо считать редакционным долгом backlog, а не доказательством готовности к безусловному старту.

### Решение Keeper

**ADM-PURE не нужно дробить просто ради загрузки второго исполнителя.** Его gate, приложения, цели, runs и findings образуют связный пользовательский путь; искусственное деление может породить красивый реестр без честной связи с результатом запуска.

Правило запуска:

- если ER-0 подтверждает чистую границу, Boss ведёт Editor semantic stream, Flash — ER-3, а ADM-PURE остаётся следующим самостоятельным эпиком;
- если ER-0 требует совместного изменения одного контура, Boss остаётся на Editor, Flash получает **отдельный** ограниченный ADM-PURE slice: UI-состояния, фильтры, доступность и acceptance-smoke поверх согласованного поведения, без самостоятельного gate/domain решения;
- ADM-PURE нельзя называть полностью параллельным, пока не определено, откуда берутся реальные runs/findings/policies и как пользователь доходит от карточки до результата.

То есть ответ Максиму: **сейчас разумнее сначала натянуть Editor до честной parity, а второго не заставлять изображать независимую работу над тем же Explorer. Второму либо даём безопасную visual-карточку в Editor после ER-0, либо отдельный ограниченный ADM-PURE UI-поток.**

## 9. Acceptance gates Editor Reborn

### Gate R0 — Truth gate

Сравнение старого и нового Editor завершено по parity matrix. Есть список gaps и принятое решение по каждому. Никаких «production-ready» без оговорки про Explorer.

### Gate R1 — Navigation gate

Все шесть корней, поддержанные folders/leaves, selection, open, create/rename/delete и empty/error states работают в новом Editor.

### Gate R2 — Continuity gate

Studio ↔ Editor, draft, dirty-guard, save, conflict, commit/diff, run/debug/evidence относятся к одному workspace и не теряют контекст.

### Gate R3 — Visual gate

Dark/light, reference-размеры, narrow viewport, длинные имена, errors, dirty и раскрытие уровней проходят проверку. Guide rails и иконки не являются приблизительной имитацией.

### Gate R4 — Safety gate

Нет plaintext-секретов, тихих перезаписей, ложного `passed` из-за сбоя, фантомных вкладок и второго browser runtime.

### Gate R5 — Owner gate

Максим открывает новый Editor и без объяснений выполняет: найти сущность → открыть → изменить → сохранить → увидеть diff → запустить → перейти к результату → переключить поверхность и вернуться. Только после этого Editor Reborn можно переводить из `evolve` в готовый backlog-эпик.

## 10. Риски и защита от повторного проёба

| Риск | Как распознать | Защита |
|---|---|---|
| «Flat list» снова объявят Explorer | В дереве нет корней/папок, но есть красивые строки | Gate R1 требует семантическую parity |
| Два дерева начнут расходиться | В Studio и Editor разные действия или названия | Один поведенческий контракт, один владелец семантики |
| Visual polish оторвётся от живых данных | На mock rows всё красиво, на error/dirty/folder states ломается | Flash принимает только живые состояния после ER-0 |
| Закрытые PK-WB возможности не подключатся к документу | Diff/run/debug открываются без правильного выбора | Gate R2 требует один end-to-end flow |
| ADM-PURE станет отвлекающим параллельным проектом | Готовы карточки, но неясен источник связей runs/findings | Сначала определить контракт результата; не дробить ради часов |
| Старые иконки/rails тихо заменят generic UI | Сравнение с reference проходит только «на глаз» | Отдельный visual gate и dark/light checklist |
| Отчёт о тестах подменит приёмку | «352 green» есть, а Explorer не виден в сценариях | Принять по поведению, не по количеству тестов |

## 11. Что остаётся за пределами Editor Reborn

- полный rewrite Studio и существующего DSL;
- изменение машинного контракта без отдельного решения;
- новые типы сущностей, новые права и новая серверная модель;
- новый browser runtime или новый runner;
- новая AI-автоматизация, не нужная для Explorer ↔ Editor flow;
- полное проектирование ADM-PURE в этом документе;
- удаление старого Studio Explorer до прохождения Gate R5;
- косметическое «улучшение» канонических иконок и rails без reference-проверки.

## Финальная позиция Keeper

Брат, фундамент они сделали серьёзный, но продуктовый Editor им засчитать нельзя: Explorer в новый вход не приехал. Это не повод выбрасывать Workbench и не повод переписывать старый Editor. Правильная стратегия — **Editor Reborn как controlled integration/parity epic**:

1. зафиксировать правду и контракт;
2. вернуть единое семантическое дерево;
3. подключить к нему уже закрытые Workbench-возможности;
4. параллельно отдать Flash только безопасную визуальную parity-зону;
5. если граница не чистая — отправить Flash в отдельный ADM-PURE UI slice, а не в драку двух Explorer;
6. закрыть работу только глазами оператора и Максима.

Пока это не выполнено, статус должен звучать так: **PK-WB foundation — closed; Editor Reborn — evolve; ADM-PURE — не начинать вслепую как будто интеграционного долга нет.**
