# MONITOR-PLAYHEAD: единый playhead + скраббер логов и видео на все view Monitor

`lane: evolve`

## Тезис

Все три view Monitor (`focus`, `observer`, `split`) получают **единый playhead**: горизонтальный timeline-ползунок под хедером + таймер `текущее / общее`. Двусторонняя связь: ползунок ↔ таймер — две проекции одного `currentTime`. От playhead зависят **логи** (какой момент показывают) и **видео** (на какой момент перемотан VNC/WebM). Мотается и вперёд, и назад. Это не фича одного view, а универсальный слой поверх всего Monitor.

Амбициозно: если впилим — 100 из 100.

## As-built якорь

### Что уже есть
- `orchestrator/static/live/index.html` — три режима `data-live-view="focus" | "observer" | "split"`. CSS grid перестраивается под каждый.
- События: NDJSON + SSE `/api/diary?channel=all`, каждое с полем `ts` (unix timestamp). `createLogPane()` — append-only фильтруемый лог, **но без скраббинга по времени**.
- Видео: VNC через noVNC `<iframe>` (`:7900`), **один живой поток**, без записи и seek.
- Статус: `refreshMeta()` / `applyMeta(meta)` опрашивает `/api/meta` каждые 2 секунды.
- `renderStatus()` — статус-дот (offline/онлайн/прогон/пауза).
- Времени-потока как такового нет: события приходят в реальном времени, плеера/playhead нет.

### Чего нет (предстоит построить)
- **Playhead** — канонический `currentTime`/`currentFrame`, общий для таймера, ползунка, лога и видео.
- **Скраббинг лога по времени** — `reduce(events[:n])` до момента `currentTime` и перерендер лог-панели. События с `ts > currentTime` не показываются.
- **Seek видео** — записанное видео (FBS/WebM) должно уметь прыгать на момент `currentTime`. Живой VNC — не умеет (live-only), но в replay-режиме (MON-5/MON-7) видео должно слушаться playhead.
- **Двусторонняя связь** — двигаешь ползунок → таймер обновляется → логи и видео перематываются. Меняешь таймер (ввод) → ползунок простраивается → то же самое.

## Что сделать (контракт, не реализация)

### Playhead (один на всё)
```js
const playhead = {
  currentTime: 0,        // секунды от начала прогона (или frame-номер)
  duration: 0,           // общая длительность (max ts событий или длительность видео)
  playing: false,        // воспроизведение / пауза
  speed: 1,              // скорость
};
```

- `currentTime` — единственный источник правды для всех view.
- Таймер = `форматировать(currentTime) / форматировать(duration)`.
- Ползунок = `currentTime / duration` × 100% (или frame-based масштаб).

### Скраббинг лога (все view)
- Каждый `LogPane` получает `filterByTime(events, playhead.currentTime)` — показывать только события с `ts ≤ currentTime`.
- Ползунок влево → лог «отматывается» назад (меньше событий видно).
- Ползунок вправо → лог «разворачивается» вперёд.

### Скраббинг видео (все view, где есть запись)
- Если VNC-сессия записана (MON-5): транскод в WebM → `<video>` с `video.currentTime = playhead.currentTime`.
- Если живой VNC (прогон идёт): видео = live, скраббинг видео недоступен, но **лог скраббится** (можно мотать лог назад, пока видео идёт вживую).
- Если прогон завершён + есть WebM: full scrub видео + лога в обе стороны.

### Timeline-полоска (все view)
- Под хедером, **во всю ширину экрана**, во всех трёх режимах.
- Тонкая по умолчанию, expand-on-hover.
- Event-маркеры: STEP, ERROR, HIGH, scanner — клик прыгает к моменту (playhead.seek(время_маркера)).
- Сегменты: толстые = активность, тонкие = неактивность (Contentsquare-паттерн).
- Внедрение ползунка потребует перестройки пропорций 1 и 2 view (CSS grid), но выгода капитальная — единый горизонт на все режимы.

### Ленивое видео в 3-м view (split 50/50)
- Если видео скрыто (пользователь в split-view смотрит только лог) — видео не грузить и не мотать вхолостую.
- При переключении из split в focus/observer — **playhead.state сохраняется**, видео подхватывается с того же `currentTime` и доигрывается как ни в чём не бывало.
- Если в split видео всё же видно (половинка экрана) — скраббинг работает как везде.

## К какому FRIEND дозреет

К FRIEND «Runtime-shell / Live» — playhead + скраббер — ядро мониторинга. Возможно, отдельный тонкий FRIEND `MONITOR-PLAYER`.

## Честная «не обещаем»

- Живой VNC не умеет seek — только лог скраббится в реальном времени.
- Полный video seek требует MON-5 (запись FBS → WebM), без этого видео-скраббинг только в replay-режиме.
- Event-маркеры требуют индексации событий по `ts`; если поток огромный — нужен sampling/bucketing.
- Frame-based timing (а не секунды) — предмет выбора; здесь ориентир — секунды как минимально достаточное.
- Точный дизайн ползунка и таймера — предмет отдельной полировки.
- **Ползунок во всю ширину** ломает текущие пропорции 1/2 view — это отдельная работа по вёрстке grid, но она обязательна (must).
- **Ленивое видео**: решение «не грузить скрытое видео» — оптимизация; если окажется, что проще грузить всегда, грузим всегда. Главное — сохранение `playhead.currentTime` при переключении view.

## Best practice (см. research)

- Единый `currentTime`/`currentFrame` — source of truth для превью, таймера и ползунка.
- Frame-based timing для точности (reactvideoplayer.com, CapCut).
- Event-маркеры на timeline — прыжок к STEP/ERROR без слепого скраббинга (Sentry, Flexxi).
- Thick/thin сегменты = активность/неактивность (Contentsquare).
- Таймер `elapsed / total` + skip-back/skip-forward + speed (Grafana).
