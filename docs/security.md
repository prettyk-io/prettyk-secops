# Безопасная эксплуатация PrettyK

> PUBLIC detail. Тезисы hub: [`canon/security-lab.md`](canon/security-lab.md) (**CANON**). Roles: [`canon/runtime-shell.md`](canon/runtime-shell.md).

Лабораторные compose-файлы демонстрируют интеграцию и не являются защищённой конфигурацией.

## 1. Разрешённая область проверки

До запуска владелец процесса обязан зафиксировать:

- владельца целевой системы;
- перечень разрешённых доменов, IP-адресов и маршрутов;
- виды допустимых действий, включая spider, active scan и фаззинг;
- временное окно и ограничение нагрузки;
- тестовые учётные записи и допустимые изменения данных;
- контакт для аварийной остановки;
- срок и место хранения результатов.

`security_configuration.allowed_extra_domains` в alpha является декларативным полем. Оно не ограничивает сетевой доступ ZAP и не заменяет ACL.

Запрещается направлять доказательный манифест на публичную или боевую систему без отдельного разрешения. OWASP Juice Shop должен запускаться локально либо в выделенной лабораторной сети.

## 2. Модель доверия

Доверенными считаются:

- авторизованный CI-процесс или оператор;
- проверенный манифест;
- хост оркестратора;
- хранилище секретов;
- выделенный Docker Engine;
- утверждённые образы и зависимости.

Недоверенными по умолчанию считаются:

- целевая система и её ответы;
- содержимое страниц и API;
- данные, полученные ZAP;
- внешние манифесты;
- публичные реестры образов;
- лабораторные учётные данные;
- отчёты до классификации.

Манифест — исполняемый вход: он может инициировать HTTP-запросы, браузерные действия, скрипты и сканирование. Манифест от недоверенного автора нельзя запускать без проверки.

## 3. Критические риски лабораторного стенда

### 3.1 ZAP без API-ключа

`services/docker-compose.zap.yml` задаёт:

```text
api.disablekey=true
api.addrs.addr.name=.*
api.addrs.addr.regex=true
```

Любой субъект с сетевым доступом к порту `8080` может управлять сканером. Официальная позиция ZAP: `api.disablekey` и широкий `api.addrs` — **только** в полностью изолированной lab ([FAQ API key](https://www.zaproxy.org/faq/why-is-an-api-key-required-by-default/)). Для общей среды необходимо:

1. включить API-ключ;
2. ограничить список адресов (не `.*` вне airgap);
3. публиковать API только на служебном интерфейсе;
4. фильтровать исходящий трафик ZAP;
5. журналировать управляющие обращения.

Industrial-профиль: [`services/docker-compose.zap.industrial.yml`](../services/docker-compose.zap.industrial.yml) (`ZAP_API_KEY`, `ZAP_API_ADDRS`; оркестратор — `KDT_ZAP_API_KEY` / `ZAP_API_KEY`). Lab default `disablekey` не обещаем в прод. Порт `8099` / Webswing `:8199` также не должны быть доступны из недоверенной сети: MITM-прокси.

### 3.2 Браузерная ферма (Selenium Grid)

Лабораторный remote-стек — Selenium Grid 4 (hub + node) с noVNC. Docker socket в контейнеры фермы не монтируется: компрометация node не даёт прямого управления Docker-хостом через socket (закрытие прежнего риска Selenoid/S-06).

Порты Grid (`4444`) и noVNC (`7900`/`7901`) по-прежнему нельзя публиковать за пределы loopback или выделенного служебного сегмента: любой с доступом к хабу может запускать браузерные сессии. Для промышленной среды нужна отдельная ферма с формализованной моделью доступа.

### 3.3 MITM и `acceptInsecureCerts`

Браузер принимает сертификат ZAP через `acceptInsecureCerts`. Это необходимо для инспекции HTTPS, но отключает обычную гарантию подлинности сертификата внутри тестовой сессии.

Мера применяется только к эфемерному профилю браузера. Запрещается:

- использовать тестовый профиль для обычной работы;
- устанавливать CA ZAP в корпоративное доверенное хранилище без согласованной процедуры;
- передавать через тестовую сессию реальные пользовательские секреты;
- заменять настройку флагом `--disable-web-security`.

### 3.4 DefectDojo

Лабораторный compose содержит:

- `admin` / `admin`;
- демонстрационные ключи приложения и шифрования;
- пароль PostgreSQL в открытом виде;
- `DD_ALLOWED_HOSTS=*`;
- HTTP без TLS;
- образы `latest`.

Такой экземпляр нельзя подключать к общей сети и нельзя использовать как реестр реальных находок. Промышленный DefectDojo разворачивается отдельно с TLS, внешним хранилищем секретов, ролевой моделью, резервным копированием и закреплёнными версиями.

### 3.5 Playground API (опциональный tool)

`data_playground.py` — не chrome продукта. Слушает только `127.0.0.1:8765`, но отправляет `Access-Control-Allow-Origin: *`. Для локальной разработки. Не слушайте на `0.0.0.0` и не публикуйте порт без аутентификации и ограниченного CORS.

API симулирует действия и не является изолированной средой исполнения недоверенного кода.

## 4. Секреты

Слои секретов:

- **Маскирование** — `Секрет` и авто-имена (`password`/`login`/…) скрывают известные plaintext-значения в логах, diary/Live, Allure и playground (`DataStream.mask_for_log`). Точный текст маски — деталь runtime, на него нельзя опираться как на контракт.
- **Шифрование в JSON** — значение можно хранить как `pk:enc:v1:…` (Fernet); при загрузке манифеста оно расшифровывается по `PK_MANIFEST_KEY`. Утилита: `orchestrator/tools/encrypt_manifest_secret.py`. Ключ не хранится в репозитории.
- **Ссылка на секрет** — `${ENV:VAR}` или `secretref:VAR` получает значение из окружения при загрузке; оно попадает в список маскирования.

«Везде скрыто» при MITM ZAP недостижимо: прокси видит трафик; цель — не светить секреты в git, логах, Allure и на диске. Лента Live маскирует известные значения потока — не замена политике стенда; см. [`monitoring.md`](monitoring.md) §4.

Authoring UI (Форма/Редактор): режим B маскирует известные секретные поля в preview/export, но authoring draft в `localStorage` остаётся рабочими данными. Поэтому production-секреты нельзя вводить в форму или конструкторы: используйте `${ENV:VAR}` / `secretref:VAR` и защищённое окружение. Это ограничение authoring UI, а не замена ASVS 14.3.

Реальные токены, пароли и cookies запрещено:

- коммитить в Git;
- хранить в примерных манифестах;
- передавать аргументами командной строки;
- прикреплять к Allure или ZAP-отчёту;
- выводить в журнал без маскирования.

Рекомендуемый канал — защищённые переменные CI или корпоративное хранилище секретов. Доступ выдаётся на время прогона по принципу минимальных полномочий.

Минимум:

- токен DefectDojo — только импорт в конкретный engagement;
- тестовая учётная запись цели — без прав реального пользователя;
- секреты ZAP и браузерной фермы — отдельные для каждой среды;
- автоматическая ротация после утечки или демонстрации.

Alpha принимает часть auth-данных из манифеста. Это функциональная возможность, а не рекомендованный способ доставки секретов.

## 5. Изоляция сети

Лабораторные порты:

| Порт | Компонент | Риск |
|---:|---|---|
| `4444` | Selenium Grid / UI (`/ui/`) | запуск сессий; список сессий в Grid UI |
| `7900` / `7901` | noVNC (Chrome / Firefox) | живой экран браузера во время прогона |
| `5050` | allure3-secops (канон) | чтение отчётов, запуск генерации и очистка результатов |
| `5051` | allure-light-secops (legacy) | чтение отчётов, запуск генерации и очистка результатов |
| `8080` | ZAP API (daemon) | полное управление сканером |
| `8099` | прокси ZAP (daemon) | перехват и маршрутизация трафика |
| `8082` | ZAP Webswing UI | удалённый Desktop ZAP (concurrent stand) |
| `8090` | ZAP API (Webswing) | управление вторым процессом ZAP |
| `8199` | прокси ZAP (Webswing) | MITM второго процесса |
| `8081` | DefectDojo | доступ к реестру находок |
| `3000` | Juice Shop | намеренно уязвимая цель |
| `8765` | API песочницы | разбор и симуляция языка |
| `8767` | PrettyK Live | ленты сценария и проверок, noVNC iframe |

На concurrent-стенде одновременно живут **два** MITM-прокси: daemon `:8099` и Webswing `:8199`. Оба — только lab/loopback; сайты и алерты между процессами не делятся. UI Webswing `:8082` даёт полный Desktop ZAP в браузере — **не** публиковать за пределы изолированного интерфейса (см. [`webswing-daemon-stand.md`](webswing-daemon-stand.md)).

Все порты должны слушать только loopback-интерфейс или выделенный служебный сегмент. Juice Shop запрещено публиковать в корпоративную или публичную сеть.

Исходящий доступ ZAP ограничивается разрешёнными целями. DNS-имена, перенаправления и ссылки внутри страницы должны учитываться в модели SSRF и выхода за разрешённую область.

## 6. Артефакты и журналы

Allure, ZAP XML/HTML, снимки экрана и видео могут содержать:

- URL и параметры;
- заголовки авторизации и cookies;
- тела запросов и ответов;
- персональные данные;
- внутреннюю топологию;
- воспроизводимые сведения об уязвимостях.

Для `reports/` требуется:

1. доступ только участникам проверки;
2. шифрование на носителе и при передаче;
3. установленный срок хранения;
4. безопасное удаление;
5. запрет публикации как общедоступного CI-артефакта;
6. очистка перед повторным использованием стенда.

Импорт в DefectDojo не отменяет необходимость управлять локальной копией XML.

## 7. Quality gate

Quality gate возвращает код `2`, если ZAP сообщает alert уровня `KDT_GATE_SEVERITY` и выше. По умолчанию порог — `High`; допустимы также `Medium`, `Low` и `Informational`. Это контроль пайплайна, но не полная политика допуска.

Поведение при сбоях задаёт runtime:

- не удалось прочитать алерты ZAP: по умолчанию fail-closed (`KDT_QUALITY_GATE_ON_ALERT_ERROR=closed`) и код `2`; `open`/`fail-open` разрешает обратное только явно;
- не сгенерировался Allure: по умолчанию только журнал; `KDT_REQUIRE_ALLURE=1` требует успешный результат и даёт код `1`;
- не выполнился импорт DefectDojo: по умолчанию только журнал; `KDT_REQUIRE_DEFECTDOJO=1` требует успешный результат и даёт код `1`.

Интеграционный пайплайн должен включать обязательность тех артефактов, без которых он не может принять результат, и сохранять `run_summary.json` вместе с ними.

`KDT_QUALITY_GATE=0` допустим только для диагностики. Отключение quality gate в релизном пайплайне требует отдельного согласования и записи причины.

## 8. Цепочка поставки

Alpha не подтверждает готовность к airgap:

- используются `latest` и `latest-release`;
- отсутствует единый перечень образов с закреплёнными digest;
- нет оформленного автономного комплекта поставки;
- не описаны импорт, подпись и проверка образов;
- нет SBOM поставки и процедуры анализа уязвимостей компонентов.

Минимум для воспроизводимой поставки:

1. закрепить версии и digest всех образов;
2. сформировать SBOM;
3. проверить лицензии и известные уязвимости;
4. подписать артефакты;
5. документировать перенос в закрытый реестр;
6. запретить сетевую загрузку во время прогона.

## 9. Контрольный список перед запуском

- [ ] область и время проверки согласованы;
- [ ] промышленная цель не используется без явного разрешения;
- [ ] исходящий доступ ограничен;
- [ ] ZAP API не доступен недоверенной сети;
- [ ] используются тестовые учётные данные;
- [ ] секреты поступают из защищённого канала;
- [ ] каталог результатов имеет ограниченный доступ;
- [ ] определена аварийная остановка;
- [ ] оператор понимает значения кодов процесса;
- [ ] после прогона проверены журнал, quality gate и обязательные артефакты.

Архитектура и коды процесса описаны в [`prettyk.md`](prettyk.md), запуск — в [`stand.md`](stand.md).  
Двухосевой допуск (exit 0/1/2) и содержимое акта для ИБ: [`admission-act-ib.md`](admission-act-ib.md).
