## 1. Оценка идеи

### Оценка галлюцинации

**24 / 100 галлюцинации.** То есть идея на 76/100 здравая.

Разумное ядро:

- пользователь описывает намерение человеческим языком;
- система превращает намерение в проверяемый рабочий каркас;
- модель задаёт вопросы там, где данных не хватает;
- результат можно увидеть, принять, подтянуть в workspace и запустить;
- завершение определяется не красивым DSL, а выполненным исходным намерением.

Галлюцинация начинается там, где «управляющая модель» должна бесконечно
самостоятельно писать, дискаверить, чинить, запускать и уведомлять. Без границ это
не co-pilot, а неконтролируемый оператор с дорогим циклом ошибок.

### Главная продуктовая формулировка

**Buddy не является вторым редактором и не является автономным владельцем
workspace. Buddy — управляющий слой, который переводит намерение оператора в
reviewable изменения и доказательство выполнения.**

## 2. Что именно доказываем

### Гипотеза

На одном разрешённом тестовом Web-приложении пользователь может в чате Studio
описать один проверяемый сценарий обычным языком. Buddy извлекает из описания
структуру приложения и намерение сценария, задаёт ограниченное число точных
вопросов, показывает preview page object + scenario, после явного подтверждения
создаёт их в рабочем пространстве, запускает ограниченный фоновый процесс и
возвращает evidence, доказывающий или опровергающий исходное намерение.

Проверяем не «умеет ли модель много», а держится ли контракт:

```text
user intent
  → normalized project skeleton
  → clarification questions
  → reviewable preview
  → explicit approval
  → workspace proposal
  → bounded background run
  → evidence against original intent
```

## 3. Минимальный сценарий PoC

### Ограничения стенда

- одно разрешённое локальное или тестовое веб-приложение;
- один оператор в Studio;
- один чат Buddy;
- один пользовательский journey из 2–4 действий;
- один page object и один scenario;
- только безопасные тестовые значения;
- запуск только в изолированном операторском/тестовом контексте;
- никакого production и никаких внешних уведомлений.

### Happy path

```gherkin
Given: оператор открыл Studio и чат PrettyK Buddy
  And: выбрано разрешённое тестовое веб-приложение
When: оператор описывает приложение, например:
      «Это SPA. Есть каталог, карточка товара и корзина.
       Пользователь открывает товар, добавляет его в корзину
       и видит товар в корзине»
  And: оператор отправляет описание предполагаемого сценария
Then: Buddy показывает извлечённый skeleton:
      страницы, переходы, намерение и ожидаемый результат
  And: явно отмечает неизвестные или предположительные места
When: оператор отвечает на уточняющие вопросы и подтверждает preview
Then: Buddy предлагает один page object и один scenario
  And: оператор видит diff/preview до изменения workspace
When: оператор принимает предложение
Then: в workspace появляется ровно один согласованный scenario
  And: запуск можно начать из Studio
  And: фоновый процесс показывает состояние, preview действий и кнопку Stop
When: тест завершается
Then: Buddy сопоставляет evidence с исходным намерением
  And: сообщает pass только если все заявленные проверки доказаны
  And: показывает, какое именно evidence подтверждает каждый результат
```

### Минимальные входы

PoC должен принять три вида естественного ввода:

1. **Описание приложения:** тип приложения, основные области, известные страницы.
2. **Список страниц:** свободный список страниц или состояний, включая неполные
   сведения.
3. **Описание сценария:** порядок действий пользователя и ожидаемый результат.

Оператор может дать всё одним сообщением или несколькими сообщениями. Buddy
должен собрать их в одну видимую рабочую гипотезу, а не считать каждое сообщение
новым независимым проектом.

## 4. Где нужен интеллект, а где достаточно алгоритма

### Интеллект Buddy / микромоделей нужен для

- извлечения сущностей, страниц, переходов, действий и ожиданий из свободного
  текста;
- обнаружения противоречий: например, страница упомянута как существующая, но
  сценарий требует другого состояния;
- определения пробелов и составления минимального набора уточняющих вопросов;
- превращения расплывчатого «оформить покупку» в проверяемую цепочку намерений;
- сопоставления пользовательского намерения с наблюдаемыми элементами и
  состояниями приложения;
- выбора, какие проверки докажут исходное пожелание, а не просто дадут зелёный
  запуск;
- объяснения провала: не найден элемент, неверное состояние, не выполнено
  ожидаемое условие или исходное требование оказалось недоопределённым;
- предложения следующего шага после провала без тихого изменения ручной правки.

### Алгоритмами и обычными правилами лучше делать

- валидацию структуры и обязательных частей skeleton;
- дедупликацию страниц, сценариев и шагов;
- проверку переходов и ссылочной целостности;
- лимиты времени, числа итераций и размера изменений;
- diff, approval, Stop и состояния фонового процесса;
- redaction секретов;
- проверку фактического результата по формальным assertions;
- журналирование событий и связь результата с исходным intent.

### Дополнительные перспективные use cases

Это хорошие кандидаты после первого PoC, но не часть его DoD:

1. **Gap analysis:** «каких страниц, состояний или проверок не хватает для этого
   пользовательского пути?»
2. **Risk-based coverage:** «какие сценарии критичны для покупки, входа,
   прав доступа и денежных операций?»
3. **Intent-to-evidence:** связать фразу требования с конкретным наблюдаемым
   доказательством, а не только с успешным HTTP-ответом.
4. **Failure triage:** после падения отличить дефект приложения от устаревшего
   локатора, неполного требования и проблем окружения.
5. **Scenario variation:** предложить негативные варианты — пустое поле,
   отказ, повторная отправка, истёкшая сессия — только как reviewable proposals.
6. **Exploration planning:** выбрать следующий безопасный участок приложения,
   если текущий сценарий упёрся в неизвестное состояние.
7. **Requirement repair:** заметить, что «пользователь видит успех» не является
   проверяемым условием, и предложить уточнение.

## 5. Роль модели и выбор модели (решение владельца · 26 авг 2026)

В PoC не закрепляем конкретный Qwen-бренд, размер или версию как окончательные.
Модель остаётся **swap-контрактом**, а не фундаментом продукта. Полный bounded
PoC выбора провайдера зафиксирован в
[`2026-08-26-ai-provider-matrix.md`](2026-08-26-ai-provider-matrix.md).

**Решение владельца по контурам:**

| Провайдер | AirGap | Non-AirGap |
|---|---|---|
| Deterministic Buddy | всегда доступен | всегда доступен |
| Local Qwen | optional, локально | optional, локально |
| Gemini Flash | скрыт и не вызывается | optional, только при явном включении |

Local Qwen используется для ограниченных операций: извлечение intent, страниц,
действий и ожиданий, подготовка skeleton, уточняющие вопросы и объяснение
bounded failure. Gemini может помочь со сложным разбором только в non-AirGap.

Ни один provider не получает право менять scope, policy, workspace или finding
status без deterministic validation и явного approval. Pass выдаётся только по
фактическому evidence.

Кандидаты сравниваются на одинаковом наборе задач и hardware. Побеждает не самая
крупная или маркетингово «умная» модель, а та, которая меньше выдумывает, лучше
сохраняет intent, укладывается в ресурс scanner-профиля и даёт проверяемый
результат. 27B/35B не являются default-целью без отдельного доказательства.

Существующий self-hosted Qwen-контур и его acceptance-набор используются как
baseline, но конкретный artifact до benchmark, resource test и license check не
утверждён.

## 6. Фоновый процесс и границы автономности

Фоновый процесс разрешён, но только как **bounded run**, а не как бесконечный
самостоятельный агент.

Обязательные свойства:

- оператор видит, что процесс запущен, что он делает и на каком шаге находится;
- есть preview создаваемых или предлагаемых изменений;
- есть явный Stop;
- число итераций и время ограничены;
- каждое изменение workspace проходит отдельное явное подтверждение либо входит
  в заранее подтверждённый текущий run scope;
- ручные правки не заменяются молча;
- при отсутствии уверенности Buddy останавливается и задаёт вопрос;
- после завершения сохраняется связь `intent → proposal → run → evidence`.

Фраза «пока не сделает» в PoC трактуется как: **до первого доказанного результата
или до честного bounded failure**, а не до бесконечной попытки любой ценой.

## 7. Отрицательные сценарии

### Недостаточно данных

```gherkin
Given: описание содержит «купить товар» без страницы, действия или результата
When: Buddy анализирует intent
Then: Buddy не создаёт выдуманный scenario
  And: задаёт минимальные вопросы
  And: показывает состояние incomplete
```

### Противоречивые данные

```gherkin
Given: в одном сообщении корзина находится на /cart,
      а в другом оператор утверждает, что корзины нет
When: Buddy собирает skeleton
Then: противоречие явно показано
  And: генерация и запуск заблокированы до решения оператора
```

### Reject / no approval

```gherkin
Given: Buddy показал preview изменений
When: оператор отклоняет его или закрывает preview
Then: workspace, draft и существующие сценарии не меняются
  And: фоновый процесс не стартует
```

### Ошибка запуска

```gherkin
Given: proposal принят, но тестовое приложение недоступно
When: оператор запускает bounded run
Then: Buddy показывает failed/disconnected state
  And: не сообщает pass
  And: показывает последнюю подтверждённую причину и evidence
```

### Превышение лимита

```gherkin
Given: процесс не может завершить сценарий в пределах лимита
When: лимит времени или итераций исчерпан
Then: процесс останавливается
  And: Buddy сообщает bounded failure
  And: перечисляет, что доказано и чего не доказано
```

### Секрет или чувствительное значение

```gherkin
Given: оператор вводит тестовое значение, похожее на пароль или токен
When: Buddy строит preview, run trace или evidence
Then: plaintext не показывается и не сохраняется
  And: используется redacted value или placeholder
```

### Ручная правка

```gherkin
Given: оператор вручную изменил locator или шаг
When: Buddy повторно анализирует тот же участок
Then: ручная правка сохраняется
  And: Buddy показывает observation или suggestion
  And: тихой замены нет
```

## 8. Критерий успеха

PoC получает `PROMOTE`, если на фиксированном тестовом приложении одновременно
выполнены все условия:

1. Свободное описание приложения и сценария превращается в понятный skeleton.
2. Buddy задаёт вопросы только по реальным пробелам или противоречиям.
3. До approval workspace не меняется.
4. После approval создаются ровно один page object и один scenario в preview и
   в рабочем пространстве.
5. Фоновый run видим, ограничен по времени/итерациям и останавливаем оператором.
6. Запуск использует живое разрешённое тестовое приложение, а не mock success.
7. Итоговый pass выдан только после проверки исходных assertions.
8. Для каждого assertion показано подтверждающее evidence.
9. При провале показана честная причина, а не зелёный результат.
10. Reject, incomplete, contradiction, disconnected, timeout, redaction и manual
    edit проходят negative checks.
11. В процессе нет тихого перезаписывания workspace и plaintext-секретов.
12. В диагностике видна цепочка `intent → proposal → run → evidence`.

## 9. Критерий провала / KILL

Текущий подход получает `KILL`, если обнаружено хотя бы одно:

- модель выдумывает страницы, действия или assertions и выдаёт их за факты;
- изменения попадают в workspace до явного approval;
- Buddy сообщает pass без evidence по исходному намерению;
- фоновый процесс нельзя остановить или он бесконечно повторяется;
- ручные изменения оператора молча затираются;
- disconnected/timeout маскируются под успех;
- plaintext secret попадает в preview, trace, log, workspace или evidence;
- Studio показывает красивый skeleton, но созданный сценарий нельзя реально
  запустить;
- одна и та же сущность расходится между preview, workspace и результатом запуска.

`KILL` означает снести конкретную реализацию PoC и сохранить полезную гипотезу
для перепроектирования. Это не означает убить идею co-pilot.

## 10. Не входит в PoC

- полный автономный AI-оператор без ограничений;
- бесконечный self-healing и самовольная смена scope;
- весь сайт, crawler и полный discovery-граф;
- все типы действий и все виды assertion;
- production persistence, multi-user collaboration и retention policy;
- Slack/Discord/почтовые уведомления;
- ZAP, Dojo, Allure и полноценный evidence pack;
- мобильные браузеры и матрица окружений;
- выбор окончательной модели или брендинг PrettyK Buddy;
- массовая генерация тестов по всему приложению;
- автоматический commit, deploy или изменение production stand.

## 11. Handoff после одобрения PoC

Это пока не команды на реализацию. После отдельного решения о запуске PoC зоны
будут разделены так:

- **Boss:** контракт intent/skeleton, orchestration, bounded run, связь
  proposal/workspace/evidence, redaction и negative behavior.
- **Flash:** чат в Studio, вопросы/ответы, preview/diff, run status, Stop,
  отображение skeleton и результата глазами оператора.
- **Keeper:** проверяет только наблюдаемое поведение, критерии PROMOTE/KILL и
  отсутствие подмены PoC production-фичей.
- **Buddy:** не входит в этот PoC без отдельной команды владельца.

## 12. Финальный вердикт Keeper

**PROMOTE в PoC.** Ядро здравое и потенциально сильное: это не «чатик рядом с
формой», а слой, который замыкает намерение пользователя на исполняемое
доказательство.

Но в первый спайк пропускаем только один bounded journey, один page object,
один scenario и один живой тестовый запуск. Если сразу разрешить Buddy
«самому ебаться пока не сделает» на всём приложении, мы получим не проверку
гипотезы, а генератор красивой неопределённости.

PoC-код после `PROMOTE` не становится production автоматически. Для production
обязателен новый Plan с отдельными контрактами, безопасностью, persistence,
наблюдаемостью и расширенными тестами.
