## 1. Брифинг: мы можем всё

До сегодняшнего дня мы были ограничены унаследованным стеком. Ant Design появился в проекте не по выбору, а по необходимости: RJSF требовал компонентную базу, Monaco требовал окружение, банковский контур диктовал одобренные библиотеки. Теперь RJSF выпилен, Monaco остался осознанно, а коробочная модель снимает любые внешние ограничения. Мы впервые можем выбирать стек не по принципу «что разрешено», а по принципу «что лучше».

PrettyK Studio — это Web IDE. Не админка, не дашборд, не лендинг. Это рабочая среда оператора, где центральными элементами станут графовый канвас сценариев и встроенный CDP-браузер. Под эти два элемента нужен фронтенд, который не просто «работает», а даёт ощущение скорости, точности и профессионального инструмента. Мы проектируем не форму ввода данных, а среду, в которой оператор проводит часы.

Современный React-ландшафт 2026 года даёт нам четыре свободы: свободу от vendor lock-in (shadcn/ui — код наш, не закрытая зависимость), свободу от лишнего CSS (Tailwind v4 позволяет собирать только используемые стили), свободу от хрупкой стилизации (headless-компоненты, где поведение отделено от внешнего вида), и свободу от медленного рендеринга (canvas-based граф, селективные обновления и измерения вместо обещаний на словах). Мы можем собрать стек, который объективно лучше подходит для Studio, чем унаследованный набор инструментов.

## 2. Видение DeepSeek: инженерный фундамент

Предложенный специалистами из Поднебесной стек — хороший верхний список кандидатов, но не готовое решение «поставить всё сразу». Для Studio важны не только популярность и скорость разработки, но и контроль над кодом, работа в airgap, предсказуемое поведение на больших графах, доступность, размер поставки и способность долго поддерживать продукт своей командой.

### Кандидатный стек

| Слой | Кандидат | Почему подходит | Что нужно проверить |
|---|---|---|---|
| Runtime | React 19, Vite текущей стабильной линии, TypeScript | Зрелый экосистемный фундамент и быстрый локальный цикл | Совместимость существующих Monaco, Playwright UI и тестового контура |
| UI-примитивы | shadcn/ui + Radix | Исходный код компонентов находится у нас; поведение и accessibility отделены от внешнего вида | Единый API компонентов, keyboard navigation, лицензии транзитивных пакетов |
| Стилизация | Tailwind CSS v4 + CSS custom properties | Быстрая сборка интерфейса, явные токены, отсутствие зависимости от `.ant-*` | Не допустить утечки utility-классов в смысловую модель дизайна; замерить итоговый CSS |
| Графовый канвас | React Flow / xyflow | React-native модель нод, кастомные edges, zoom, selection, minimap и хорошая база для редактора | Большие графы, история изменений, copy/paste, клавиатура, экспорт и совместимость с нашим Wired |
| Кодовый редактор | Monaco Editor | Полноценная IDE-модель, diff, несколько моделей и зрелое поведение для DSL | Web Workers, размер поставки, сохранение keep-alive и отзывчивость на слабом рабочем месте |
| Клиентское состояние | Zustand для UI и доменного состояния | Один простой слой для темы, панелей, графа и команд; меньше скрытых границ | Не смешивать его с серверным кэшем и внутренним состоянием React Flow |
| Серверное состояние | TanStack Query или эквивалентный query-слой | Кэширование, retries, invalidation и явные состояния загрузки | Airgap-поставка, правила кэширования и граница с Live |
| Runtime-проверка | Zod или генерация типов из контракта | Ошибка контракта обнаруживается на границе, а не глубоко в UI | Не создать второй независимый SoT вместо Pydantic/Wired |

**Почему не нужно сразу добавлять Jotai к Zustand.** Jotai действительно хорош для атомарного состояния, но двойная система состояний без доказанной потребности усложнит диагностику и передачу проекта. Сначала нужен один понятный store для состояния приложения, внутренний store React Flow для механики канваса и отдельный query-слой для сервера. Jotai можно рассмотреть позже, если профилирование покажет реальную проблему лишних перерисовок.

### Сравнение UI-подходов

| Подход | Сильная сторона | Цена решения | Вывод для Studio |
|---|---|---|---|
| shadcn/ui + Radix | Максимальный контроль и владение кодом | Компоненты нужно собирать и поддерживать самим | Основной кандидат |
| Mantine | Много готовых компонентов и быстрый старт | Более выраженный собственный визуальный характер и меньше свободы на уровне primitives | Хороший запасной вариант, если скорость важнее уникальности |
| HeroUI / React Aria | Сильная доступность и готовая визуальная база | Нужно проверить соответствие сложному IDE-интерфейсу и долгосрочную устойчивость экосистемы | Кандидат для отдельных паттернов, не решение по умолчанию |
| Ant Design | Низкая миграционная стоимость | Наследие, тяжёлые оверрайды и чужая визуальная модель | Legacy-слой на время перехода |

### Сравнение графовых библиотек

| Библиотека | Лучше всего подходит для | Ограничение |
|---|---|---|
| React Flow / xyflow | Редакторов, где нода — React-компонент, а пользователь постоянно взаимодействует с графом | Историю, доменные команды, persistence и часть сложного поведения нужно проектировать самостоятельно |
| Cytoscape.js | Больших аналитических графов и визуализации связей | Менее естественная модель для богатых React-нод и редакторских контролов |
| G6 | Визуализации крупных графов и специализированных алгоритмов раскладки | Более специфичный API и дополнительная адаптация к продуктовой модели |

Для первой реализации наиболее разумен **React Flow**, но его нельзя принимать на веру только по числу звёзд. До утверждения решения нужен небольшой performance spike на наших сценариях: сотни нод, сложные связи, частое перемещение, выделение группы, undo/redo, copy/paste, восстановление из Wired и работа с клавиатуры. Undo/redo и история доменных изменений — это часть PrettyK, а не обещание сторонней библиотеки.

### Лицензии и airgap

Все кандидаты должны проходить не только проверку собственной лицензии, но и проверку дерева транзитивных зависимостей. Для каждого релиза коробки нужны зафиксированный lockfile, license inventory, SBOM, локальный кэш пакетов и проверка запуска без доступа к интернету. Формулировка «MIT» — необходимое условие, но не заменяет аудит поставки.

**Утверждённый стек (2FA):** React 18 + Vite 8 + TypeScript 6, shadcn/ui на Radix, Tailwind CSS v4, React Flow / @xyflow/react, Monaco, Zustand. React Flow — новый слой для canvas-редактора сценариев, не замена существующему entity-графу. antd — legacy, вытесняется поэтапно. Подробный канон — [`sanctuary/pure/studio-stack.md`](pure/studio-stack.md).

**Миграция с antd — поэтапная.** Новый Studio-shell появляется рядом со старым интерфейсом. Существующие страницы не переписываются ради чистоты дерева. Design tokens из текущей системы становятся основой нового визуального контракта, а legacy-компоненты постепенно выводятся из рабочих поверхностей.

## 3. Видение Luna: архитектурные границы и контракты

Редизайн — не только про цвета и кнопки. Это перестройка фронтенд-контрактов вокруг рабочего поведения оператора. Студия должна быть единой средой, а не набором страниц, случайно соединённых общей шапкой.

### Четыре слоя визуальной архитектуры

1. **Design tokens** — единственный источник визуальной истины: цвет, типографика, радиусы, тени, плотность, состояния фокуса и motion. Токены должны описывать смысл (`surface`, `text-muted`, `danger`), а не конкретный оттенок.
2. **Component primitives** — доступные базовые компоненты с клавиатурным поведением, фокусом, aria-состояниями и контрактом ошибок. Их внешний вид не должен зависеть от antd.
3. **Product patterns** — повторяемые паттерны Studio: node card, inspector, command palette, run console, browser toolbar, finding row, empty state и recovery state.
4. **Studio shell** — резиновая рабочая поверхность с изменяемыми панелями, запоминаемым расположением и режимом фокуса. Граф, браузер, код и журнал не должны конкурировать за одно и то же пространство.

### Критическая граница: CDP управляет браузером, но не рисует его поверхность

Встроенный CDP-браузер нельзя проектировать как обычный `iframe`. Playwright и CDP дают управление страницей, события, DOM, accessibility и сетевые данные, но визуальная поверхность браузера — отдельный транспорт. Поэтому до большой UI-миграции нужно зафиксировать два связанных, но разных контракта:

- **Control plane:** URL, состояние страницы, выбранный элемент, действие оператора, запись шага, прогресс выполнения и ошибки.
- **Display plane:** live-viewport, screenshot или video-поток, масштабирование, выделение элемента и переход между ручным и автоматическим режимом.

Если целевой сайт не разрешает iframe, продукт не должен притворяться, что это обычная веб-вкладка. Studio должна дать понятный fallback: управляемую визуальную поверхность с теми же действиями, подсветкой и состояниями. Это важнее конкретной технологии отображения.

### Контракт с бэкендом

Pydantic/Wired остаётся единственным machine-контрактом. Новый фронтенд не создаёт параллельную модель, не меняет смысл Wired ради удобства компонента и не переносит бизнес-логику в визуальный слой. Live, Allure, Dojo и AI-интеграции сохраняют свои границы. На фронтенде нужны только явные состояния: loading, ready, stale, offline, error и recovery.

### Стоп-гейты

- Не начинать массовую миграцию до утверждения одной user journey: открыть Studio → увидеть граф → открыть браузер → записать действие → запустить → понять результат.
- Не выбирать графовую библиотеку до performance spike на реальном Wired и реальных командах редактирования.
- Не считать CDP-браузер готовым, пока отдельно не проверены управление, отображение, resize, accessibility и redaction секретов.
- Не добавлять второй state-слой без профилирования и понятной границы ответственности.
- Keep-alive для Monaco и тяжёлых рабочих поверхностей сохраняется, если переключение вкладки не должно уничтожать контекст пользователя.

### Метрики shipped behaviour

Готовность редизайна определяется не числом переписанных компонентов. Оператор должен быстрее собрать сценарий, не терять изменения при переключении поверхностей, видеть связь между нодой и браузерным действием, восстановиться после ошибки и работать без интернета. Дополнительно измеряются время первого интерактивного состояния, задержка перемещения ноды, число лишних перерисовок, keyboard coverage, accessibility и размер airgap-поставки.

## 4. Видение Gemini: визуальный язык, холст и эргономика

PrettyK Studio создаётся не как учётная система или дашборд с таблицами, а как полноценная среда пространственного конструирования. Когда оператор часами исследует сложные приложения, интерфейс должен давать ощущение физической точности, визуальной тишины и мгновенного тактильного отклика.

### Главные герои: графовый канвас и живой браузер

В новой архитектуре Studio две центральные доминанты, которые делят между собой фокус внимания:

1. **Графовый канвас сценариев (Infinite Scenario Canvas)**
   - **Анатомия нод:** каждый узел — это функциональный блок (страница, форма авторизации, мутационный фаззер, шаг сканирования, точка ветвления или assert-проверка). Узлы имеют строгую визуальную иерархию: статус выполнения (idle, active, passed, alert), входные и выходные порты данных, компактные индикаторы селекторов и бейджи времени.
   - **Семантический зум (LOD — Level of Detail):** на общем плане граф показывает топологию атаки и переходов между страницами; при приближении раскрываются конкретные DSL-шаги и параметры; на максимальном зуме доступен инлайн-редактор локаторов и проверок.
   - **Связи и потоки данных:** интеллектуальная трассировка ребер (ortho / smooth bezier) с интерактивными бейджами, подсветкой активного потока данных во время запуска и визуализацией точек ветвления.
   - **Пространственные инструменты:** группировка (frames/boxes), миникарта со световым окном вьюпорта, lasso-выделение, авто-выравнивание (auto-layout) и быстрый поиск по графу с центрированием камеры.

2. **Интегрированный браузерный контур (Live Browser Twin)**
   - **Синхронная пара с холстом:** браузер и граф работают как единый организм. Клик по ноде на графе подсвечивает связанный элемент в браузере; выбор элемента в браузере подсвечивает или создает соответствующую ноду на канвасе.
   - **Инспекция и запись:** поверх вьюпорта накладывается легкий интерактивный слой: рамки найденных элементов с приоритетом локаторов (T0–T4), бейджи доступности, индикатор перехвата сетевых запросов и кнопка быстрого добавления шага в сценарий.
   - **Гибкая пространственная раскладка:** холст и браузер могут работать в режиме сплита (50/50, 70/30), полноэкранного канваса с плавающим окном браузера (picture-in-picture) или режима глубокой кодовой инспекции.

### Визуальные принципы и дизайн-система

- **Эстетика точного инструмента:** ориентир на визуальную культуру лучших профессиональных редакторов (Figma, Blender Node Editor, Linear, Raycast). Четкая геометрия, матовые темные поверхности с деликатным микро-контрастом, отсутствие визуального мусора и навязчивого декора.
- **Цветовая дисциплина:** нейтральная глубокая база (charcoal / zinc / slate) для снижения усталости глаз. Акцентный фирменный циан используется строго для фокуса, интерактивности и активного состояния. Семантические цвета (зеленый — чистый результат, янтарный — предупреждение/фаззинг, красный — уязвимость) работают как навигационные сигналы, а не фон.
- **Командная строка и клавиатурный поток:** палитра быстрых команд (`Cmd+K` / `Ctrl+K`) для создания нод, переключения режимов, запуска сканеров и поиска по проекту без отрыва рук от клавиатуры.
- **Типографическая шкала и ритм:** строгая модульная сетка (4px / 8px). Интерфейсный шрифт Golos UI для высокой читаемости мелких подписей в портах и панелях; моноширинный JetBrains Mono для DSL, селекторов и логов.
- **Осмысленная микро-динамика:** физически корректные переходы (120–180ms ease-out), пульсация активных потоков данных на графе во время исполнения, мягкая подсветка фокуса и строгая поддержка режима `prefers-reduced-motion`.
