# FEATURE-ADMISSION: конвейер допуска фич в коробку

> **CANON** — hub topic. Slice: **16 августа 2026** (2FA: зачисление по явной просьбе владельца).
> Как фича/идея попадает в pure-коробку (`prettyk-pure`), включая ништяки, «подсмотренные» у Cosmo.
> Реестр: [`INDEX.md`](INDEX.md). Смежное: [`split-canon.md`](split-canon.md) (коробка vs интеграция),
> [`enterprise-friends-required.md`](enterprise-friends-required.md) (планка enterprise),
> [`friend-lifecycle.md`](friend-lifecycle.md) (коридоры идей). Патчи через 2FA.

## 1. Зачем

Коробка не должна наполняться «по наитию»: взяли в Cosmo, скопировали, заодно притащили банковскую
специфику. Нужен **один маршрут допуска**, по которому фича либо заезжает в коробку, либо остаётся в
пакете, либо дозревает. Cosmo — источник **идей**, а не источник кода для копипаста.

## 2. Два входа

| Вход | Что это | Куда |
|---|---|---|
| **Фича изнутри** | Родилась в коробке, без привязки к заказчику | `dev` (коробка) |
| **Ништяк из Cosmo** | Идея/фича, «подсмотренная» в интеграции (пример: notification) | extract-процедура → `dev` (только после §4) |

Оба входа проходят один и тот же конвейер ниже.

## 3. Route-вердикт (на старте)

| Вердикт | Смысл | Куда |
|---|---|---|
| **pure** | Общая ценность для отрасли, без банковской специфики | в коробку (`dev`) |
| **custom** | Специфика ЦБ (роли, лесенка, бланки, deploy-цепочка) | в cosmo-каталог, в коробку **не** |
| **evolve** | Про продукт, но сыро / зависит от незакрытого | backlog § «Сырое / evolve» |

**Граница:** CANON-код не импортирует из custom; custom может импортировать из коробки (`split-canon.md`).

## 4. Extract из Cosmo — выкорчёвывание (не копипаст)

Ништяк из Cosmo попадает в коробку **только** через явную extract-карту. Шаги:

1. **Исходник** — где живёт в `cosmo/` или `sanctuary/custom/cosmoport2/cosmo/`.
2. **Отделить идею от специфики** — что генерализуемо, а что намертво банковское (роли, домены,
   реквизиты, формулировки ЦБ).
3. **Точка генерализации** — как идея переформулируется в отраслевую (не «как у банка»).
4. **Extract-карта** в `docs/feature-routing-backlog.md`:

```text
ID: EXTRACT-<n>
Исходник: <файл/блок в custom>
Идея: <что берём, без банковской специфики>
Специфика, которую НЕ берём: <роли/домены/реквизиты/бренды ЦБ>
Куда: <целевой путь в коробке>
DoD-гейты: см. §5
Вердикт: pure (дозрело) / evolve (рано)
```

**Правило:** не выдёргивать «заодно». Каждый ништяк — отдельная карта. Копипаст с банковской
спецификой — инцидент.

## 5. DoD коробки (специфичные требования допуска)

Фича допускается в `pure`, только если **все** пункты:

| # | Требование | Как проверяем |
|---|---|---|
| 1 | **Никакой утечки заказчика** — нет брендов, ролей, доменов, реквизитов, формулировок ЦБ | `rg` по имени банка/доменов/реквизитов в коде и доках — пусто |
| 2 | **Генерализация** — работает на любом контуре, не только на ЦБ | нет hardcoded доменов/портов/ID заказчика |
| 3 | **Поведение глазами заказчика** — результат виден, не «мок вызван» | приёмка по UI/acceptance |
| 4 | **Точечный smoke-тест** | умеренный тест под фичу, не весь suite |
| 5 | **Machine-контракт синхронизирован** — при изменении формы/контракта обновлены Pydantic-модели `orchestrator/models/wired.py` (+ legacy `docs/wired.json` если нужно) | `schema-sot.mdc` |
| 6 | **Не нарушает honest-contract и стены** | `honest-contract.md`, `walls.md` |
| 7 | **Ничего наружу** — фича не отдаёт телеметрию/аналитику третьим сторонам | `admin-integrations.md` |

DoD-гейты проверяет Keeper/Максим при приёмке. Тоннель — дисциплина, не CI-автоматика.

## 6. Полный цикл допуска (канон)

```text
фича / ништяк из Cosmo
   │
   ▼
1. route-вердикт  ──┬─ pure   → коробка
                    ├─ custom → cosmo-каталог
                    └─ evolve → backlog «Сырое / evolve»
   │
   ▼
2. extract (если из Cosmo) — отделить идею от банковской специфики
   │
   ▼
3. DoD конвейера (§5) — пройдены?
        ├─ нет → остаётся в пакете / возвращается в evolve
        └─ да  → Friend request на основе фичи (friend-lifecycle.md)
                    │
                    ▼
                4. 2FA (ритуал канона)
                    │
                    ▼
                5. pure / canon (CANON seeker → member)
```

**Правило:** прохождение DoD конвейера — **предусловие**, а не сам канон. Фича, прошедшая гейты,
оформляется как Friend request → 2FA → зачисление в `pure`/canon. Движение фичи и полировка hub
связаны именно так: **DoD конвейера → Friend request → 2FA → pure/canon**.

## 7. Честные границы

- Не вводит отдельные git-ветки под stable/release — версии тегами на `main` (`split-canon.md`).
- Работа в двух энвах одновременно — **не сейчас**; Cosmo живёт каталогами в том же дереве.
- DoD-гейты проверяет Keeper/Максим; зачисление в canon — только через 2FA (`friend-lifecycle.md`).
- Ништяк, не прошедший DoD, остаётся в пакете или возвращается в `evolve`.

## 8. Связь с enterprise-планкой

Допуск фичи в коробку не тождественен прохождению [`enterprise-friends-required.md`](enterprise-friends-required.md).
Планка enterprise — про **готовность продавать** (SSO, RBAC, аудит, airgap). Конвейер допуска — про
**как идея/фича становится частью коробки**. Фича может заехать в коробку, но коробка при этом ещё
не enterprise. Не путать «приняли фичу» и «прошли планку».
